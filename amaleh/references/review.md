# Fresh cross-model review

DeepSeek writes → GLM reviews; GLM writes → DeepSeek reviews. Kimi work gets a capable different family. Host work gets no model review; see [host work is final](#host-work-is-final). Different provider for one model is not independence. Supply fresh read-only context containing intent, criteria, standards, actual changed files, relevant callers and check receipts. The pi reviewer gets the task's diff and the tail of each check's output, and a turn budget of `reviewerMaxTurns`, so it starts from what changed instead of rediscovering the repository. A check that failed beside other checks and then passed alone carries `unstable.failedOutput`; the reviewer judges whether the task's change causes that failure, such as a race, a shared file or port or a timing dependency, and files a blocking regression when it does. See [check isolation](runtime.md#check-isolation). A reviewer call also stops at its wall-clock limit, `reviewerTimeoutMs` (default 2400000 ms, 40 minutes; `0` disables the limit), and a reviewer call that fails or times out is recorded as a failed speed sample with its elapsed time, so reviewer speed reflects its failures too. Exclude the author's reasoning and proposed verdict. The reviewer may trace affected consumers beyond the diff. A reply that is not a valid report is asked for once more with the exact rejection reason, in the reviewer's own pi session, so the inspection it already did is kept rather than bought again. The review and its correction count as one reviewer call in the speed measurement.

One reviewer groups baseline lenses: Spec/requirements, Standards/simplicity, correctness and omissions. Keep Spec and Standards coverage separate in the report. The reviewer is asked to report every blocking defect it can find in this one pass and not to stop at the first, while grouping lenses that describe one root defect into a single finding, because each missed defect costs a full repair round. Jev selects added lenses grounded in real changed behavior: money/error paths, contracts, security/authorization, migrations, visual/accessibility, resources, dependencies, test quality or observed performance. Additional focused review can run in parallel for sensitive behavior. For native multiple reviewers consolidate all findings into one `review` receipt without losing original reports; archive originals.

Every finding needs a reachable scenario and evidence. Distinguish observations from inference and new defects from unrelated inherited problems. A taste preference is not a defect. Blocking is narrow: a regression of existing behaviour, a failed task criterion, a false statement in documentation the task changed, or vendor code or setup for a third-party service that the task added with no source in the workspace or the task's references is always blocking; a preference, style choice or optional improvement is never blocking and belongs in the report as non-blocking. Vendor code means what a worker cannot check by running it: an embed or tag snippet, a vendor call's argument order, the steps in a vendor console. The reviewer traces each one to the file it was copied from, because a model writing it from memory produces code that looks right and is not. Concurrency needs an actual overlap/retry/shared-state path. A payment-total bug requires expected monetary outcomes, not just spec prose. Archive and group duplicate claims without suppressing valid evidence.

Inside `delegate`, [the Jev gate](#the-jev-gate) judges every blocking finding against the blocking definition and the owner of its file before a repair is bought. Serious disputed defects require evidence inspection or main-model diagnosis; no confidence score can dismiss a failing test, because the gate judges findings only and a failing check always goes to repair. Obtain a corrected independent report for refuted findings; do not silently edit a review into a pass. `repair` increments the persistent counter and chooses Flash, Kimi, then host takeover; see [the repair ladder](runtime.md#the-repair-ladder). No reset through rename, new commit or restart; replanning retains ancestry.

Default: two ordinary Flash repair cycles, then one Kimi diagnosis/repair cycle; after that the actual invoking model diagnoses and changes strategy. A defect that survives a repair goes up the ladder at once instead of waiting for the count: to Kimi after a Flash repair did not remove it, and to the host after the Kimi repair did not remove it. That budget is the user's policy, and `configure` changes it only with the user's quoted instruction. Reopening an accepted chunk with `invalidate` spends a cycle too, so a probe the coordinator runs after acceptance belongs in the task's checks before delegation. Only the reopened task pays: its dependents carry no defect of their own, so they spend nothing, and an accepted dependent keeps its output and is checked and reviewed again, with no worker run, once its upstream is integrated again and merged into its checkout. The exception is a dependent whose own last attempt had already failed a check or a review: its next worker run repairs that failure, so it returns to `ready` and spends a cycle. `invalidate` records a defect reopen. An `amend` without feedback that asks an accepted task for more — a new goal, changed criteria or a new check id — is a defect reopen too: it needs a probe that fails on the unchanged checkout (or `noProbe`), spends a cycle and counts; see [reopening accepted work](runtime.md#reopening-accepted-work). Any other `amend` records a contract reopen. Only defect reopens count in the reopen health warning and `metrics.reopenedChunks`, so an amendment that only changes bookkeeping such as `resources` is not reported as a defect the checks missed. The probe must fail on the unchanged checkout before the reopen is recorded. Reopening for shaped user feedback is the exception: it is new scope and spends none. An `amend` spends a cycle only when the task is in review with a failing check other than `scope`, or with an open blocking finding, or when it asks an accepted task for more, because only then is the next worker run a repair. An `amend` that changes nothing but `resources` on a task holding a finished output with no open blocking finding keeps that output: the next `delegate` re-runs checks, `scope` and review on it with no new worker run and no cycle. With an open blocking finding the same amend is a repair, so it spends a cycle and the worker runs again; widening `resources` never buys a fresh review. A new `result` drops the review of the output it replaces, so one finding is never charged twice. Initial review is not a repair cycle. The review after a repair reads the repair only; see [the review after a repair](#the-review-after-a-repair). Reuse conclusions only while inputs remain valid. Stop repetitive strategy, not authorized work; never use loop bounds to ship defects. At integration review new interactions and invalidated conclusions rather than automatically re-running every lens.

Before `finish`, run all integration checks and ask Jev whether each outcome claim is supported by the actual referenced evidence. Resolve uncertainty yourself with evidence. Record a concise claim/evidence explanation per acceptance criterion. The host owns this semantic acceptance judgment; CLI check success alone cannot prove the product is correct.

## File ownership

A task owns the files its `resources` match. The review packet carries the task's `resources` and `otherTasks`, each other task with the resources it owns. The reviewer prompt states the rule: a defect in a file outside the task's resources, which the task's changes did not cause, is filed with `blocking: false` and names the owning task; a regression the task's own change causes is the task's defect wherever the symptom shows. Without this rule a reviewer blocks a task for a file the task may not edit, the repair worker cannot fix it, and the chunk burns its whole repair budget on a defect that belongs to someone else.

## The Jev gate

Every time a chunk is about to buy a repair, `delegate` first asks Jev several questions in one call. One call, because a single yes-or-no answer gives a worker nothing to act on, and three separate calls would cost three round trips for one decision. The call carries the task contract, the blocking definition, the other tasks with their resources, the failing checks, the open blocking findings (the first 12) each with the owner of its file, and the cause of the previous repair. The questions are:

- `course`: which repair course fits — `targeted` (the smallest correct fixes), `rethink` (the approach is wrong) or `simplify` (the implementation is too complex). The chosen course reaches the repair worker as guidance.
- `progress`, asked only when the task already had a repair: `new` when every defect listed now differs from the previous round, `same` when at least one is a defect the last repair did not remove. `same` at confidence 0.85 or more moves the task up [the repair ladder](runtime.md#the-repair-ladder) at once.
- `finding_<index>`, one per open blocking finding: `fix-here`, `other-owner` or `not-blocking`.

A finding is settled, and stops blocking, only when Jev answers `other-owner` or `not-blocking` at confidence 0.85 or more. Below that, or on any API failure, the finding stays blocking and the repair runs: the gate can only remove work, never add a verdict of its own. Code enforces the one hard fact: `other-owner` is refused for a finding whose file the task owns, whatever the confidence. A settled finding keeps its text and gains `settled: {verdict, owner?, confidence}`; a `finding-settled` event records it, the `jev-gate` trail stage lists it, and every `delegate` outcome lists it under `settledFindings`. When every finding of a review is settled, the review no longer holds the chunk: a coverage entry with status `finding` is then paid. One unsettled finding keeps the whole review blocking.

An `other-owner` finding is handed to the task that owns the file: the next brief of that task carries it under "Defects handed to this task". When no task owns the file, the owner is `host`, and the finding stays in the outcome for the coordinator. A handed finding is shown once: a worker run that already received it does not receive it again.

The gate removes a reviewer's blocking verdict on Jev's judgment alone, so read `settledFindings` at the chunk boundary. `health` counts them in `metrics.reviews.findingsSettledNotBlocking` and `metrics.reviews.findingsHandedToOwner`. A failing registered check is never settled by the gate.

## The review after a repair

The first review of a task reads the whole change. The review after a repair does not start again from nothing: `delegate` continues the first reviewer's own pi session, on the same model, and asks it to verify the repair. The reviewer gets `sessions/<task>/repair-review.md`, which lists the blocking findings it filed and the findings the run settled, and `sessions/<task>/repair-diff.patch`, which holds only what changed since its review. It decides for each of its findings whether the defect is gone, files a new finding only for a blocking defect the repair diff introduces, and never files a settled finding again. Its reply has the same shape as a first review, with full coverage. A second full review by a fresh model re-reads the repository and finds a new set of small defects each round; that loop is what made a simple chunk cost four reviews.

The repair diff is the difference between two Git trees: a snapshot of the task checkout taken at the first review, and one taken now. The snapshot uses a temporary index, so it changes neither the checkout nor its staging area. Each review records a `review-session` event `{id, model, sessionDir, tree, review, followUp?}`.

A fresh full review by another eligible family runs instead when the follow-up cannot be trusted or cannot run: the task contract changed since that review (an `amend`, a `review-check`, an `invalidate`), no repair followed it, the checkout is outside Git, the session directory is gone, the first reviewer's model is no longer eligible, or the caller excludes that reviewer's family — the coverage-debt retry and the reviewer failover both do. The repair worker is routed away from the reviewer's family, so the reviewer that continues its session stays independent of the author of the repair. `health` counts follow-up reviews in `metrics.reviews.ofRepairOnly` beside `metrics.reviews.total`.

## Scope questions

A failing `scope` check does not start a repair. Only the coordinator knows whether the task's `resources` were too narrow or the worker changed files it did not own. `delegate` returns `escalated` with stage `scope-question`, the out-of-scope paths and the worker's output artifact, and `next` returns `scope-question` until the coordinator answers. To keep the paths, `amend` the task's `resources`: the output is kept and verified again with no new worker run and no cycle, and any path the new resources still leave out is reverted by a repair. To revert them all, delegate the task again: the loop runs a repair that spends a cycle, because the worker overreached. Each path is asked about once per task. A later worker run that keeps a path already asked about is a failed repair and spends a cycle; only a path nobody was asked about raises a new question. The question is saved in the same state revision as the failing `scope` receipt, so an interrupted delegate never leaves a scope failure without its question.

## Contract questions

A worker sometimes cannot deliver the contract as written: a registered check cannot pass for a reason outside the task (it compares text the platform rewrites), two criteria contradict each other, or the work needs vendor code no source in the workspace or references supplies. Bending the work to satisfy such a contract produces a hack that passes the check and fails the user, and a reopen that costs a cycle and a full chunk round to undo. So the worker raises a contract question with the evidence it observed and finishes its run without working around it. `delegate` returns `escalated` with stage `contract-question` before any check runs, since the question may be about a check, and without spending a cycle; `next` returns `contract-question` until the coordinator answers. When the contract was wrong, `amend` it: that spends no cycle, and an amendment that changes only checks or resources keeps the output for verification against the corrected contract. When the contract stands, delegate again with a `brief` that says why; `delegate` refuses without one. The checks and review then judge the output as it stands, the brief reaches any repair worker, and a repair they need spends a cycle like any other.

## Host work is final

No model reviews work the host wrote under `host-exception`, whether the reason was `repair-escalation` or `user-request`. A Flash or Kimi reviewer that rejects host work can only send it back to the host, so the review adds a round and never changes who repairs. `delegate` runs the registered checks and `scope`, and accepts when they pass. When one fails, it returns `escalated` with stage `host-checks-failed` and puts the task back in `repair` without spending a cycle; the host takes a fresh `host-exception` to fix it. `repair` called by hand on host work does the same. The checks are the only automatic gate on host work, so before `result` the host re-reads its own diff against the task criteria and every reopen reason, and fixes what it finds.

## Coverage before verdict

Before the first review, the host maps the actual change to requirements, callers/consumers and reachable transitions. For an orchestrator, enumerate start, success, rejected preflight, failed execution, interrupted ownership and resume; inspect every operation kind sharing capacity. For a simple pure calculation, lifecycle/concurrency may be inapplicable: say why instead of inventing safeguards. Capture a trustworthy baseline/diff when claiming a defect was introduced. The pi reviewer receives the task's Git diff automatically; a native reviewer or a workspace outside Git does not.

Use `review-packet` to inspect the factual contract. It carries global outcomes, task criteria, settled decision answers (without reasoning), dependency contracts, registered commands, receipt references and their artifact directory. The reviewer must read applicable repository standards; pi disables automatic context-file loading. Do not forward the author's proposed verdict. One fresh reviewer covers the applicable obligations together. Independent host probes can run alongside code inspection under existing ownership/capacity rules.

Every review supplies `coverage`: exactly one `{id,status,evidence}` for each obligation in the packet. IDs include each task criterion, each global outcome and standards, boundaries, lifecycle, parallelism and integration. Status is `covered`, `finding`, `unreviewed` or `not-applicable`. Evidence names inspected paths/consumers, actual receipts/results, or the precise missing probe. A task reopened since its last acceptance also carries one `reopened:N` obligation per reopen reason; the reviewer confirms against the actual artifact that each named defect is gone. Criteria, outcomes and reopen reasons cannot be not-applicable; record this task's contribution or preservation and what still requires integrated verification. Fixed lenses may be not-applicable only with an explicit reason.

The runtime rejects malformed coverage and blocks acceptance for missing, unreviewed or finding entries. Old receipts without coverage remain readable but cannot authorize a new acceptance. `next` returns `review-evidence-needed` for gaps, distinct from `triage-repair` for real blocking defects. Missing evidence does not consume repair cycles. When a review leaves coverage debt and no blocking finding, the loop obtains exactly one more review from a different eligible family — not the author's family and not the family that left the gap — and accepts if that review is complete. This is separate from a reviewer call that fails without a verdict: no final text, an incomplete pi run or a provider error ends that call, so the loop replaces it with a fresh review on another eligible family whose call did not fail, bounded by `providerFailovers`, recording a `provider-failover` event with stage `reviewer`. Only a workspace escape or a settled funding or authorization failure ends the review; when the failover budget runs out, `delegate` returns `failed` and the task stays in review with its worker output, ready to delegate again. A retry that cannot be routed returns `route-pending` rather than inventing a verdict. Only a second gap escalates as `review-evidence`, and that escalation leaves the task awaiting review so the host can register the requested probe or obtain a corrected report. This enforces presence and declared disposition, not the truth of a model assertion: the host still inspects supporting evidence and uses Jev for semantic judgments.

For a missing executable probe, the host can use `review-check` with `{id,check:{id,command,args,role}}` while verification is idle, then `check`. The role is required: `"probe"` or `"guard"`. This retains repair ancestry and invalidates the prior review so a fresh corrected receipt must consider the new evidence. Read-only reviewers request probes; they do not execute commands. For missing source inspection, re-open only the identified paths and produce a corrected full coverage ledger. Reuse valid conclusions, never auto-fill gaps as covered. If repeated probes do not settle the same uncertainty, the host diagnoses or requests actual higher effort instead of buying the same review repeatedly.

Acceptance is followed by serial integration and registered whole-feature checks. Inspect changed cross-task interactions; task-level coverage cannot establish that independently correct changes compose correctly. Historical escapes become discriminating regression probes under the relevant obligation. Adding reviewer count alone is not evidence of better coverage.

Reviewer context includes only settled decisions explicitly marked `purpose: "requirement"`. Use that purpose for user/product requirement facts, never finding disposition, routing or completion judgments. Unclassified legacy decisions stay durable for the host but are withheld from the fresh reviewer; restate relevant requirements in task criteria/constraints or classify them explicitly. This prevents prior verdicts leaking through otherwise factual-looking answers. Previously accepted/completed historical records are not retroactively re-reviewed; the new gate applies to new acceptance transitions.
