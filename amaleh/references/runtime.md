# Command contract

Run `bun <skill>/scripts/cli.ts <operation> <workspace> <run-id> [input.json]` by default; fall back to `node <skill>/scripts/run.ts ...` only when Bun is absent, since modern Node directly executes the erasable TypeScript. Paths are arguments, not interpolated shell commands. There are no npm runtime dependencies.

Printing never changes what an operation returns. A machine caller always reads JSON, because JSON stays the default whenever stdout is not an interactive terminal. A person at a terminal instead gets a readable report — a headline answering the question, then aligned detail rows — from `doctor`, `list`, `status`, `health`, `next`, `diagnose` and `preflight`; every other operation pretty-prints its JSON. Pass `--json` to force the machine record even at a terminal. Human output is therefore opt-in by being a person at a terminal, never by guessing, and an existing caller that parses JSON is unaffected.

`doctor` takes no run; `list <workspace>` returns one summary per run — id, status, intent, acceptance criteria, task count, revision, the run it continues and its acceptance record — newest revision first. Read it before starting anything, because later work on an existing outcome continues that run rather than opening a new one. `install` links this canonical skill into the default Claude/Codex skill directories and refuses conflicting targets. Windows uses directory junctions; Unix uses directory symlinks. `uninstall` is the inverse and takes the same optional home argument: it removes only those two links, reports each target as `removed` or `not installed`, and refuses a real directory, a file or a link that resolves elsewhere with `Conflicting skill target: <target>` while removing nothing. It never deletes the checkout itself.

## Input examples and operations

`start`: `{ "host":{"kind":"codex","model":"actual model from session"},"intent":"requested outcome","criteria":["observable success"],"constraints":["accepted restriction"] }`. Add `"continues":"<prior run id>"` to build on earlier work: the new run inherits that run's acceptance criteria and every settled requirement decision, so an accepted palette, contract or interface is not decided again from zero. Without `continues`, an intent that substantially repeats an existing run is refused and the matching run is named; `"unrelated":"<reason>"` overrides when the word overlap is coincidental. Add `"shape":{...}` with the shape of the intent (see `shape` below). Without `shape`, `next` returns `shape` and `plan` refuses until the intent is shaped. In a Git checkout with a remote, `start` fetches that remote, resolves its default branch from the remote HEAD, and refuses unless HEAD contains the fetched tip; the refusal names the remote branch (for example `origin/main`) and the Git commands that fix it. Input `base.userInstruction`, quoting the user, overrides the refusal and is recorded with the quote. A workspace outside Git, or with no remote, records a `base-unverified` event with the reason and proceeds; a failed fetch refuses with the Git error unless `base.userInstruction` is given. Create each run branch from that fetched default branch, and keep merges in the run's integration worktree rather than the checkout the skill itself runs from.

`feedback`: `{ "text":"the user's actual words" }` records user feedback as a new request. `next` then returns `shape`, and `plan`, `amend`, `invalidate` and `delegate` refuse until it is shaped. Record feedback the moment it arrives, even while a batch is running; running chunks finish, and nothing new starts on the old understanding.

`shape`: `{ "understanding":"what is asked and what it is for", "gaps":["..."], "pushback":["..."], "additions":["..."], "mentor":["reusable principle, only when warranted"], "options":[{"id":"headline","summary":"...","gains":"...","costs":"..."},{"id":"split","summary":"...","gains":"...","costs":"..."}], "recommendation":"headline", "questions":["..."], "affects":["hero"], "chosen":{"option":"headline","quote":"the user's words"} }` shapes the latest request. Pass two to four `options` with a `recommendation`, or `clearCut` naming why the request has only one sensible reading. `affects` names delivered tasks that feedback reshapes. A shape with `questions`, or with `options` and no `chosen`, stays open: `next` returns `ask-user` with the questions, options and recommendation, and the gated operations keep refusing. Run `shape` again once the user answers. `chosen` records a `requirement` decision with the user's quote as its reason. The full shape is archived as an artifact. Runs recorded before shaping existed carry no request and are not gated. See [shape every request](planning.md#shape-every-request).

`plan`: `{ "tasks":[{"id":"charge","title":"Correct charge","goal":"Apply the agreed amount rule","phase":"checkout","deps":[],"resources":["src/checkout/**"],"criteria":["expected totals hold"],"kind":"code","checks":[{"id":"test","command":"bun","args":["test","test/charge.test.js"],"role":"probe"}]}],"integrationChecks":[{"id":"all","command":"bun","args":["test"]}] }`. Commands use executable plus argument arrays. Every check requires a `role`: `"probe"` detects the task's defect on the unchanged checkout; `"guard"` protects existing behaviour and is not subject to the probe pre-check. A code task must have at least one probe check, or a `"noProbe"` string explaining why no executable can detect the defect; `plan` refuses otherwise. These role rules, and the reserved `scope` id, apply to contracts written through `plan`, `amend`, `review-check` and `invalidate`; a run saved before they existed still loads and runs, and its checks without a role are never probe-gated. Integration checks carry no role. Resources are path globs relative to the task workspace, for example `"amaleh/scripts/adapters.ts"`, `"website/src/**"` or `"*"` for the whole workspace; a resource without a wildcard also owns everything under it. After every worker run the built-in `scope` check compares the changed and untracked paths of the task's Git diff against these globs and fails the chunk when a path matches none of them, so name the paths the task may actually touch. The id `scope` is reserved for that built-in check, so no task check may register it. Register actual project checks, not invented test commands. Research and plan tasks may have no executable checks but still need reviewed evidence. Plans may add tasks, not discard history or silently rewrite existing contracts. A task may carry `"skills":["installed-skill-name"]` and `"references":["path/to/design-contract.md"]`; the runtime reads those files at launch and inlines them into the worker's prompt, so name a skill instead of retyping its content into a brief. A bare name resolves to `SKILL.md` under the host's skills directory, a path resolves against the task workspace, and an unreadable entry fails the launch naming every path tried. One task per independently deliverable outcome: a single task carrying three or more run outcomes, or four or more of its own criteria, is refused because nothing in it can run in parallel. `"singleChunk":"<reason>"` overrides when the work genuinely cannot be divided, and the reason is recorded.

`amend`: `{ "id":"charge","reason":"actual changed requirement or diagnosis","task":{...complete updated task contract...} }` deliberately changes an existing contract while retaining identity and escalation ancestry, invalidating affected descendants, and validating the updated graph. Do not create a replacement ID merely to reset repair history. An amend spends a repair cycle only when the task is in `review` with a failing check other than `scope`, or with an open blocking finding, because only then is the next worker run a repair; the descendants it reopens spend none. An amend that changes nothing but `resources` on a task holding a finished output (in `review`, or host work returned by `host-checks-failed`) with no open blocking finding keeps that output and leaves the task in `review`, so the next `delegate` re-runs checks, `scope` and review with no new worker run. An amend answers a pending scope question: any out-of-scope path the new resources still leave out is reverted by a repair. An amend also answers an open contract question (see `delegate`), and then spends no repair cycle; when it changes nothing but `checks` or `resources` on a task holding a finished output with no open blocking finding, it keeps that output in `review`, so the next `delegate` verifies it against the corrected contract with no new worker run. The `contract-amended` event records `keepsOutput`, `charged` and `answersQuestion`. Descendants of the amended task are sent back as `invalidate` describes: an accepted one keeps its output for verification. Add `"feedback":true` when the amendment delivers shaped user feedback that names this task in `affects`; the reopen then spends no repair cycle. Each task can be reopened once per feedback. `amend` records its reopen as a contract reopen and `invalidate` as a defect reopen: the reopen health warning and `metrics.reopenedChunks` count only defect reopens, so an amendment that only changes a task contract is not reported as a defect the checks missed. Feedback reopens are recorded separately and stay uncounted.

`next`, `status`, `resume`, `html`: no input. `status` includes durable references and phase status. `html` returns a local HTML progress artifact.

On a new host/model, pass `resume` an input with `host: {kind, model}` containing the actual current coordinator. The handoff retains the prior identity in history and allows escalation to the current host. Completed runs resume as `done` without mutation.

`effort-configure`, `effort-request`, `effort-start`, `effort-finish`, `effort-reconcile` implement the conditional same-model effort path; see [effort](effort.md) for validated input shapes and host execution requirements. `next` exposes requested/running passes and `status` preserves the baseline and execution receipt. A host/model switch must first reconcile any active effort pass.

`record-decision`: `{ "id":"intent-answer","question":"What outcome?","answer":"The user's actual answer","source":"user","reason":"Reference to the actual instruction" }` records settled intent without a Jev call. Use source `host` only for delegated technical decisions. Never invent a user answer. `block` accepts an optional task `id` to block only that task and its dependents while unrelated work proceeds.

`pools`: `{ "pools":[{"role":"frontend","models":["verified exact model IDs"],"requiredInputs":["text","image"],"requiresTools":true,"notes":"User preference and relevant evidence"}] }` persists purpose-specific routing preferences. Filter these against current catalog capability facts before dispatch; configuring a model does not prove eligibility.

`decide`: `{ "id":"unique-decision","question":"Which route is justified?","criteria":{"source":"Read relevant code","execute":"Evidence is sufficient"},"state":{"task":"...","facts":["..."]} }`. Use actual evidence, not empty routing ceremony. Response chooses an option or yields `host-decision`. OpenRouter Jev uses the decisions endpoint, not chat completions. `host-decision`: `{ "id":"unique-decision","choice":"source","reason":"evidence and reasoning" }`.

`decide-batch`: `{ "decisions":[{ "id":"...", "question":"...", "criteria":{...}, "state":{...} }, ...] }` settles up to sixteen independent questions in ONE gateway call and one input file. Always prefer it over repeated `decide` calls when more than one question is open; each answer is recorded individually and low-confidence entries still yield `host-decision`.

`delegate`: `{ "id":"charge", "workspace":"absolute task workspace", "brief":"optional extra guidance", "lenses":["optional review lenses"] }` hands a whole chunk to the runtime. Before the first worker launch, it runs every probe check on the unchanged checkout; a probe that passes there cannot detect the task defect, so the chunk is refused, naming the passing probe. This pre-check only applies before the first worker run: a task whose delivered output shaped feedback reopened carries that output, so its probes are not re-gated and the reopened chunk delegates normally. It then routes and launches the worker (round-robin), assembles the brief from the task contract when omitted, runs registered checks, obtains independent other-family review, applies bounded Jev course-correction, and drives repair cycles (Flash → Kimi → host) autonomously. Host work is final: when the host itself wrote the result under `host-exception`, `delegate` runs the registered checks and `scope` and accepts with no model review, reporting `hostFinal:true`; when one fails, it returns `escalated` with stage `host-checks-failed`, puts the task back in `repair` and spends no repair cycle. A task at host depth that has no finished host result returns `escalated` with stage `host-takeover` and the host model, without routing. One coordinator invocation per chunk. A task left in `review` with a recorded result and no live owner, for example after its review failed on a provider error, is delegated again straight to checks and review; the finished worker output is reused, not bought again. The same holds for an accepted dependent that a reopen of its upstream sent back to `review`; until its dependencies are accepted and integrated again, `delegate` returns `route-pending` with a `dispatch-blocked` route naming them instead of verifying it early. Such a dependent is judged in its own checkout, so that checkout must contain the upstream it depends on: while the run's main checkout HEAD is not an ancestor of the dependent checkout's HEAD, `delegate` returns `escalated` with stage `refresh-checkout`, naming the missing commit, and `next` returns `refresh-checkout`. Merge the run branch into that checkout and delegate again. A checkout outside Git cannot be compared and is verified as it stands. A `brief` given to `delegate` also reaches every repair worker the call starts, as coordinator guidance. A worker that finds the task contract itself wrong (a registered check that cannot pass for a reason outside the task, criteria that contradict each other, or vendor code it would have to write without a source) raises a contract question through the bundled helper instead of working around it, and finishes its run. Before any check runs, because the question may be about one of them, `delegate` returns `escalated` with stage `contract-question`, the `questions` and the worker's output artifact as `workerOutput`; it spends no repair cycle and no model reviews that output. `next` returns `contract-question` until it is answered. Either `amend` the contract (recorded as a `contract-answered` event with answer `amend` and the amendment's reason), or delegate again with a `brief` that says why the contract stands (answer `stands`, with the brief as its reason): the checks and review then judge the output as it stands, and the brief reaches any repair worker. `delegate` refuses a task with an open contract question when no `brief` is given, and one answer closes every open question on the task. After each worker run, and again after every repair like the registered checks, the built-in `scope` check compares the changed and untracked paths of the task's Git diff with the task's resource globs: any path matching no resource is a failing `scope` receipt whose output lists every out-of-scope path. A failing `scope` check does not start a repair: `delegate` returns `escalated` with stage `scope-question`, `outOfScope` and the worker's output artifact as `workerOutput`, spends no repair cycle, and `next` returns `scope-question` until it is answered. `amend` the task's `resources` to keep the paths, and the next `delegate` verifies the same output with no new worker run; or delegate again, and a repair that spends a cycle reverts them. The `scope-question` event is saved in the same state revision as the failing `scope` receipt, and the answer is recorded as a `scope-answered` event: `revert` when the next `delegate` starts, `amend` when an amendment arrives. Each path is asked about once per task: a later run that keeps a path already asked about is a failed repair and spends a cycle, and only a path nobody was asked about raises a new question. An unchanged checkout keeps its `scope` receipt when the task is delegated again, like the registered checks. `result` drops the review of the output it replaces. `scope` is reserved for this built-in check, so no task check may register it. A workspace outside Git has no diff; the check then records a `scope-unverified` event saying it could not run rather than passing silently. A review that leaves coverage debt without a blocking finding is retried once by a fresh reviewer from another eligible family — not the author's family and not the family that left the gap — and is accepted if that review is complete; only a second gap escalates. In the reviewer stage, any reviewer call failure other than a workspace escape or a settled funding or authorization failure is replaced by a new review on a model whose family did not fail, bounded by `providerFailovers`, and recorded as a `provider-failover` trail stage and event with stage `reviewer`; when that budget runs out, `delegate` returns `failed` and the task stays in review with its worker output. Worker-stage failover is unchanged: it still replaces only transient provider failures. Outcomes: `accepted` (chunk done, integrate next), `escalated` (repair-exhausted/host-takeover/host-checks-failed/scope-question/contract-question/review-evidence/workspace-escape — your turn to diagnose, answer, supply evidence or restore files), `route-pending` (resolve the named prerequisite), `refused` (a probe already passes on the unchanged checkout), `failed` (infrastructure error; task state preserved). A `trail` records each stage, including every `scope` verdict. Do not call `worker`/`check`/`reviewer`/`repair` manually for a delegated chunk. `delegate` also accepts `skills` and `references`, which override the task's own for this chunk.

`delegate-batch`: `{ "ids":["hero","docs","pricing"], "briefs":{"hero":"optional extra guidance for this chunk only"}, "lenses":["optional review lenses"], "skills":["optional shared skill"], "references":["optional shared contract"] }` delegates every ready chunk in one invocation, bounded by `maxWorkers`, starting the next id the moment a slot frees. Use it for one chunk too; a sequence of single `delegate` calls wastes the capacity that is already configured. Each task needs its own isolated checkout, so omit `workspace` and let each id use the workspace recorded on its task. Passing one shared `workspace`, or two tasks pointing at the same checkout, is refused before any worker starts — concurrent tasks in one checkout serialize into conflicts rather than into parallel work. Two batched tasks whose `resources` overlap never run at once: the batch holds the later one and starts it the moment the earlier one finishes, while tasks with separate resources keep running alongside. Overlap is judged conservatively: two resources overlap when the directory one of them matches under contains the other's, so `website/src/**` overlaps `website/src/lib/x.ts` and `**/*.md` overlaps everything, while `website/src/**` and `website/scripts/**` do not. Paths are compared ignoring case, backslashes, `./` and repeated slashes, and a resource containing `..` overlaps everything. The same rule decides conflicts with live tasks outside the batch, which routing reports as `dispatch-blocked` and `claim` refuses. A `briefs` key that is not in `ids` is refused. The CLI runs the batch in a detached process, because a batch lasts far longer than any host tool call. It returns `{launched, pid, ids, cursor, log}` as soon as the batch has recorded its first chunk. The detached process writes its final `{delegated, concurrency, outcomes}` report to `log`. A batch that fails before starting any chunk is reported as an error carrying the tail of that log. `"foreground":true` runs the batch inside the calling process instead and returns the outcomes directly; use it only from a script that can block for the whole batch.

`wait`: `{ "after":<cursor>, "timeoutMs":100000 }` follows running delegations. It returns as soon as a chunk has finished after `after`, a delegation's process is gone, no delegation is running, or `timeoutMs` passes. The result is `{outcome, cursor, finished, live, interrupted, next}`. `outcome` is `finished`, `interrupted`, `idle` or `still-running`. `finished` lists `{id, outcome, reason, at}` for each chunk that finished after `after`, including a chunk refused before it started. Pass the returned `cursor` as `after` on the next call, so no outcome is reported twice or missed. Without `after`, it waits for the next finish from now on. `interrupted` names delegations whose recorded process no longer runs on this host; `resume` closes them and blocks their tasks for reconciliation. `timeoutMs` is 100000 by default and 540000 at most; set it just under the host's tool timeout. `wait` only reads state, so polling it adds no revisions.

Workers consult Jev mid-task without the coordinator through the bundled helper: `node <skill>/scripts/jev.ts <workspace> <run-id> <task-id> "<question>" "<optionA>|<optionB>|..."`. Worker briefs include this automatically; calls are recorded as `worker-jev` events.

Workers raise a contract question through the second bundled helper: `node <skill>/scripts/question.ts <run workspace> <run-id> <task-id> "<what is wrong, with the evidence>" [check-id]`. It records a `contract-question` event while the task's worker runs, refuses a check id the task does not have, and tells the worker to stop working on that part and finish its run. Jev chooses between options inside the contract; the question helper is for a contract that is itself wrong.

`catalog`: fetches dated candidate cards including capability, price, and source. Select stable eligible models and record exact IDs; the description is not local performance proof. Set `AMALEH_JEV_MODEL` to a verified current OpenRouter Jev ID if the installed default becomes stale.

`claim`: `{ "id":"charge","workspace":"absolute task workspace","model":"actual selected model","routeDecisionId":"decisionId returned by route" }`. A fresh matching worker route is required and consumed atomically; an arbitrary model name is insufficient. For direct host exceptions, first call `host-exception` with `{ "id":"charge","reason":"user-request","evidence":"actual explicit user instruction" }` or reason `repair-escalation` after the persistent repair allowance is exhausted. Pass the returned `authorization` as `hostAuthorization` instead of `routeDecisionId`, with the actual host model. Grants are single-use and scope-bound. `worker` takes `{id, workspace, brief, routing?}` and selects a model automatically before it invokes pi, records real model/session output and checkpoints the result. Never concurrently run workers in the same checkout. `result`: `{ "id":"charge","output":{"changes":["..."],"remaining":[]} }`.

`check`: `{ "id":"charge","checkId":"test" }`; omit `id` for a feature integration check. Runs the registered executable, saves output and fingerprints. If a check changes files, rerun checks invalidated by those changes before acceptance.

`reviewer`: `{ "id":"charge","lenses":["Spec","Standards","money path"],"routing":{"evidence":"Relevant suitability evidence"} }` invokes a fresh read-only pi review. Its prompt asks the reviewer to report every blocking defect it can find in this one pass rather than stopping at the first, while grouping lenses that describe one root defect into a single finding. A reply that is not a valid report is re-requested once with the exact rejection reason, in the reviewer's own pi session (`--continue` against a `--session-dir` unique to that review), so the inspection it already paid for is kept. The review and its correction are one speed sample, with their elapsed time and output tokens added together; a review that never returns a valid report is recorded as failed. `review` records a review obtained through a supported native agent instead: `{ "id":"charge","model":"actual reviewer model","fingerprint":"from fingerprint operation","report":"coverage and findings evidence","findings":[] }`. Never fabricate a reviewer identity or report. Findings require id, lens, location, scenario, evidence, consequence and a boolean blocking field.

`repair`, `accept`: `{ "id":"charge" }`. Repair updates the persistent escalation counter. `integrated`: `{ "id":"charge","evidence":"actual integration and interaction inspection evidence" }` after the host integrates changes and checks compatibility. It compares the task's checkout with the accepted output, so record it before removing the task's worktree: once the checkout is gone it refuses, naming the missing path. `finish`: `{ "claims":["evidence explanation corresponding to each run criterion"] }` after all tasks integrated, full required checks pass and Jev claim-support decisions resolved. While a task is not accepted and integrated, `finish` refuses with `Incomplete tasks:` followed by each such task and its state. A finished run cannot change: any operation that would write to it refuses and names the `"continues":"<run id>"` input that starts a new run on its criteria and settled decisions. Before closing, `finish` fetches the remote default branch again and refuses while merging it into HEAD would conflict, naming the conflicting files; a workspace outside Git or with no remote is skipped with an event. These host attestations are trusted operator input, not cryptographic proof of correctness. `finish` refuses while `health` reports delegation warnings, listing each one; `"acknowledgeWarnings":"<reason>"` overrides and records a durable `health-acknowledged` event in the same revision as the finish, so a failed finish leaves no acknowledgement behind. A run that did the work by hand therefore cannot close silently.

`save`: archives any JSON evidence; returns a content ID. `artifact`: `{ "id":"artifact hash" }` retrieves original evidence. `fingerprint`: optional `{ "workspace":"task checkout" }` returns exact current content fingerprint.

`block`: `{ "reason":"external failure and intervention needed" }`. `requeue`: `{ "id":"task","evidence":"interrupted effects inspected and reconciled" }` only for blocked tasks. `invalidate`: `{ "id":"task","reason":"which accepted assumption/evidence changed" }`; repair ancestry remains. `configure` accepts positive integers for maxWorkers, flashRepairCycles, deepRepairCycles. `maxWorkers` changes freely. The repair budget is the user's policy: changing `flashRepairCycles` or `deepRepairCycles` needs `"userInstruction"` quoting the user's explicit request, which the `configured` event records. Resubmitting the current values needs none. `invalidate` counts as a repair cycle for the task it names when that task already produced output, so a reopen spends the same budget as an in-loop repair. Only that task carries the defect. Every task that depends on it is sent back too. One that was accepted, or awaiting review with no failing check and no open blocking finding, keeps its output in `review` and spends nothing: once its dependencies are accepted and integrated again and its checkout contains them, `delegate` checks and reviews it with no worker run. One whose own last attempt failed returns to `ready` and spends a cycle, because its next worker run repairs that failure; one with no output returns to `ready` and spends nothing. Feedback reopens charge nobody. The `invalidated` event lists the kept dependents as `reverified`. Reopening such a task also needs the probe that found the defect: `"check":{"id":"rendered","command":"node","args":["scripts/check-rendered.mjs"],"role":"probe"}` joins the task's checks, so every later repair of the task runs it inside the chunk loop. A check with role `probe` must fail on the task's own checkout before the reopen is recorded; a probe that passes there cannot detect the task defect, so the reopen is refused. Every other rejection of the request is decided before that probe runs, so an invalid request never executes the supplied command. A `guard` check is registered without this pre-check. Passing the same check again is accepted; a different command under an existing check id is refused. When no executable can show the defect, pass `"noProbe":"<why>"` instead. `noProbe` is accepted once per task: a second defect the checks cannot see means the checks are missing something, so the second reopen needs `check`. `"feedback":true` reopens a task named in the `affects` of the latest settled feedback shape; it needs no probe and spends no repair cycle, once per task per feedback. `unlock` verifies a dead same-host lock owner before removing a stale lock; never delete a live or unverifiable lock.

## Authentication and process settings

Use `OPENROUTER_API_KEY`, or pi's existing OpenRouter credential. The runtime never prints or writes it into artifacts. Expired pi credentials require refresh through pi. `AMALEH_PI_ENTRY` can name the installed pi JavaScript entry; the runtime picks the executable that runs it by resolving `AMALEH_RUNTIME` if set, otherwise `AMALEH_NODE` if set, otherwise `bun` found on PATH, otherwise the executable currently running the CLI. `AMALEH_NODE` is kept for existing configurations. Platform discovery checks common executable-adjacent global package locations without running shell shims. Worker calls disable external skills/extensions/context discovery; name the skills and reference files on the task instead, and the runtime hands the worker a file to read. The brief, the run context, any guidance and the reviewer's packet are all written to `sessions/<task>/` and referenced by path: a command line cannot carry them, and a file keeps the worker's own tokens paying for what it reads. A launch whose prompt still exceeds the limit is refused with the character count rather than an operating-system error. A worker that produces no output at all for `idleTimeoutMs` is treated as hung: its whole process tree is killed, the trace records an `idle-timeout` stage naming the last tool it started, and the chunk fails with that reason instead of holding a worker slot indefinitely. Set `idleTimeoutMs` to `0` to disable it. Independently of silence, every pi call stops at its wall-clock limit — `workerTimeoutMs` for a worker and `reviewerTimeoutMs` for a reviewer (defaults 5400000 and 2400000 ms, 90 and 40 minutes; `0` disables the limit). When a call passes its limit the runtime kills the whole process tree, records a `call-timeout` trace stage, and fails with a message containing 'time limit' without transient retry or length continuation. A failed or timed-out call is written to the speed ledger with `failed:true` and its elapsed time, so it counts in `metrics.modelSpeed` and slow-model routing instead of disappearing. The worker prompt names the absolute task workspace and states that every edit and write must stay under it; the brief, the run's artifacts, the Jev helper, the contract question helper and the run's main checkout are named read-only. It also forbids writing vendor code or setup for a third-party service from memory (copy it from a file in the workspace or the task's references, or raise a contract question), and requires every command to end on its own. A bash or powershell command that waits for a debugger forever is stopped at once: one whose segment launches `node`, `bun`, `deno` or `tsx` (directly, by path, or through `npx` or `bunx`) with `--inspect-brk` or `--inspect-wait`, or that assigns `NODE_OPTIONS` a value containing either flag. The runtime kills the worker's process tree, records a `debugger-wait` trace stage and fails the call with a message naming the flag, instead of waiting for `idleTimeoutMs`. A command that only mentions the flag, such as a search or an echo, is left alone, and a script that adds the flag itself is caught by `idleTimeoutMs` as before. Whichever limit stops a call first (debugger wait, turn limit, idle timeout or wall-clock limit) is the reason it reports. The runtime parses the path argument of every edit and write tool call in the worker's pi events and resolves it against the workspace. When a worker's edit or write targets a path outside the task workspace, the runtime kills the worker's process tree immediately and `delegate` returns `escalated` with stage `workspace-escape` naming every escaped path, without spending a repair cycle or provider failover. The task is left blocked with the escaped paths in its reason; the host is the only one allowed to restore files outside the task workspace, and requeues the task once they are restored. The guard sees only edit and write tool calls; bash and powershell side effects are invisible to it. A finished worker run is judged by what it changed, not by how it phrased its goodbye: a process that exits 0 with a complete `agent_end` but no final text is recorded as a result with an empty summary, and the registered checks and the reviewer decide whether the work stands. Reviewer calls still require final text, because the reviewer's reply is the JSON report it is judged by. A worker reply cut off by the model's output limit (`stopReason: length`) is continued once in the same pi session (`--continue` against the same `--session-dir`) with a short finish prompt; a second cut-off returns the partial reply so checks and review run on it. `error` and `aborted` stop reasons remain provider failures.

Model choice and runtime limits live in `amaleh/models.json`; `AMALEH_MODELS` points at a different file. Every field is validated, and a bad value names both the field and the file; `workerTimeoutMs` and `reviewerTimeoutMs` are optional and default when absent, so an existing configuration keeps loading. `flash` and `deep` are arrays of exact OpenRouter model ids — no wildcards and no family heuristics, so what runs is what you listed. Give `flash` at least two vendors: a reviewer must differ from the author's family, so a single-vendor pool leaves every task unreviewable the moment that vendor has a bad day. `jev` is the decision model, overridden per session by `AMALEH_JEV_MODEL`. `providerCooldownMs` is how long a model that exhausted its launch retries is skipped, `providerFailovers` how many times a chunk re-routes around a transient provider failure, `launchAttempts` how many times a single launch retries before giving up, `idleTimeoutMs` the silence that marks a worker hung, `workerTimeoutMs` and `reviewerTimeoutMs` the wall-clock limit for a worker and a reviewer call (defaults 5400000 and 2400000; 0 disables the limit), `reviewerMaxTurns` the most assistant turns a reviewer may take before it is stopped with a turn-limit failure (default 60), and `slowModelWindowMs` how far back routing looks for slow calls (default 604800000, seven days; 0 turns slow-model skipping off). 'Provider returned an empty response', 'Stream ended without finish_reason' and 'The model stopped before completing the response' count as transient provider failures, so both the launch retries and the chunk's `providerFailovers` route around them to another family; money, authorization and quota failures do not. They preserve pi's complete session messages and use the global configuration read-only in intent; pi may acquire its own configuration lock as part of startup.

## Diagnostic traces

`diagnose <workspace> <run-id>` returns current state, pending work, operation timelines, failures, unfinished operations and usage totals. It also works when initialization failed before a valid snapshot existed. Its `health` section (`health` operation standalone) measures delegation quality — coordinator-authored decisions per task, worker-side Jev calls, delegate vs manual dispatches, host-action ceremony, model-family distribution, contract questions (`metrics.contractQuestions`) and `metrics.coordinatorOperations`, the successful state-changing CLI operations the coordinator itself ran, which leaves out failed calls, the detached batch process (traced as `batch:delegate-batch`, and recognised in older runs as the `cli:delegate-batch` trace that starts while its launcher runs and outlives it) and read-only calls such as `health` and `fingerprint`. `metrics.revisions` is reported as a plain count with no allowance: most revisions are saved by the runtime inside `delegate`, three for every check it runs, so they measure the work, not the coordinator. Health emits warnings naming anti-patterns: coordinator micro-decisions, manual stepping through the worker→review→repair loop, decisions made at the wrong layer, excessive recording ceremony, single-family fixation, hand-made `worker`/`reviewer`/`repair`/`accept` calls outnumbering tasks alongside delegation, chunks reopened by a defect `invalidate` at least half as often as there are tasks (an `amend` that only changes a task contract, and a feedback reopen, are not counted), and one task carrying the whole feature. Use it to catch an expensive coordinator-driven run early; `finish` reads the same warnings and refuses on them. `metrics.hostTakeovers` counts every claim made under a `host-exception`, and `metrics.hostTakeoversByTask` splits that count by task; a takeover is an allowed boundary, not an anti-pattern, so it raises no warning. Every finished pi call, successful or failed, appends one line — start time, model, role (worker or reviewer), duration, output tokens and a `failed` marker — to `.amaleh/model-speed.jsonl`, shared by every run in the workspace. The first read of a missing file seeds it from the pi traces of every existing run. `metrics.modelSpeed` lists each model per role from the samples inside `slowModelWindowMs`: calls, a `failures` count, average and longest minutes per call, output tokens per second and output tokens per call; failed calls' elapsed time counts in the averages and the longest call, so a model that fails slowly is not hidden. `slowModels` names each model whose average call takes at least twice the median of its role, once that role has three models with three or more calls each. Routing skips exactly these models for that role, so the report and the router always agree. A slow model is a vendor fact, not a coordinator mistake, so it never blocks `finish`; show it to the user. Trace files live in `.amaleh/runs/<id>/diagnostics`, independently of state commits; pi session paths and immutable artifact references remain available. API attempts record HTTP status, request identity when supplied, duration and usage. pi records process identity, tool progress, exit status and protocol/provider failures. An unfinished operation means active or interrupted; inspect ownership before replaying.

Costs are separated into OpenRouter response-reported cost and pi local estimates. Neither is a reconciled billing ledger; local pi pricing can lag the gateway catalog, so compare the estimate with the OpenRouter activity page before trusting it. Totals count new input tokens and cached tokens separately (`cacheReadTokens`, `cacheWriteTokens`); a long worker call re-reads its whole context every turn, so cached tokens usually outnumber new input many times over. `health` adds `metrics.spend`, the estimated cost, calls, turns and tokens per model, per role and per task, and warns when the `deep` models in `models.json` take more than 30% of an estimated spend of at least $1. That warning blocks `finish` like the others. Missing usage is unknown, not proof of zero cost. Telemetry redacts known credentials and sensitive fields, excludes prompts and tool bodies, and limits error text. Original authorized tool artifacts and pi sessions are separate and may include project content.

`next.parallel.ready` exposes independent dependency-ready candidates even while the focus action awaits review or repair. `parallel.available` reflects worker capacity; `claim` still enforces resource and workspace conflicts. Each `parallel.running` entry carries `alive`, and `parallel.delegations` lists open delegations with their process and `alive`. When no recorded owner of a running task or active verification is alive on this host, `next` returns `resume` instead of reporting that work as running. A pending decision may concern a candidate: satisfy its real prerequisites before dispatching.

`route`: `{ "id":"charge", "purpose":"worker", "workspace":"absolute checkout", "routing":{"role":"configured optional role","requiredInputs":["text"],"contextTokens":8000,"evidence":"Observed requirements and model suitability evidence"} }`. Purpose is worker or reviewer. Role is optional; omit it for default Flash pools. Selection is deterministic round-robin across eligible models, seeded by the run's session hash and advanced per routing decision inside the transaction that records it, so concurrently dispatched chunks alternate families instead of all selecting one model; no Jev call is spent on mechanical selection. A model that exhausted its launch retries on a transient provider failure is skipped for five minutes unless every candidate is cooling down. A model that `health` names slow for this purpose is skipped too, until its slow calls age out of `slowModelWindowMs`; it stays eligible when skipping it would leave no candidate. The routing decision records each skipped model under `skippedSlow`. A successful selection returns launch plus model and decision ID, without spawning. Selecting `reassess` or finding no eligible candidates returns `route-blocked`; revise the task/pool/evidence, then route again. Explicit model values on worker/reviewer must match the selected route and cannot bypass it. Legacy pending routes still resolve through `host-decision`.

`next.parallel.actions` lists each task's verification/repair/integration stage. `parallel.independent` suggests a conflict-free check/review batch bounded by available execution slots. Dispatch these through the host concurrently; they are not additional copies of the focus action. See [parallel execution](parallelism.md). Integration remains serial in the main workspace.


### Review coverage contract

`review-packet` input `{id,lenses?}` returns factual review context and exact required coverage IDs. Each check carries the last 3000 characters of its stdout and stderr. The pi `reviewer` also receives `changes`: the task's Git diff against the merge base of its checkout and the run's main checkout, limited to the task workspace, with a file summary and the list of new untracked files. The patch is a file in `sessions/<task>/`, cut at 400000 characters. A workspace outside Git gets no diff and the old instruction to find scope evidence. Both `review` and the pi `reviewer` use coverage entries `{id,status,evidence}`, where status is covered/finding/unreviewed/not-applicable. A task reopened by `invalidate` or `amend` since its last acceptance gains one `reopened:N` obligation per reason; like task criteria, it cannot be not-applicable, and the same reasons appear in the worker's brief under "Why this task was reopened". Missing coverage in legacy receipts is retained as a gap. A finding is blocking only when it is a regression of existing behaviour, a failed task criterion, a false statement in documentation the task changed, or vendor code or setup for a third-party service that the task added with no source in the workspace or the task's references (an embed or tag snippet, a vendor call's argument order, the steps in a vendor console); a preference, style choice or optional improvement is never blocking. The packet lists the task's `references`, or those supplied to `delegate`, `reviewer` or `review-packet` for this chunk, so the reviewer can trace such code to its source. The delegate loop answers a first gap with no blocking finding by obtaining exactly one fresh review from another eligible family — not the author's family and not the family that left the gap — and accepts if that review is complete; a retry that cannot be routed returns `route-pending`, and only a second gap escalates as `review-evidence`, leaving the task in review. `review-evidence-needed` is host work, not a completed review or repair cycle. `review-check` input `{id,check:{id,command,args}}` registers an additional unique task check while review is idle, invalidates the old review, and retains repair counters. Execute it with `check`, then obtain updated independent coverage. See [review method](review.md).

Reviewer context includes only settled decisions explicitly marked `purpose: "requirement"`. Use that purpose for user/product requirement facts, never finding disposition, routing or completion judgments. Unclassified legacy decisions stay durable for the host but are withheld from the fresh reviewer; restate relevant requirements in task criteria/constraints or classify them explicitly. This prevents prior verdicts leaking through otherwise factual-looking answers. Previously accepted/completed historical records are not retroactively re-reviewed; the new gate applies to new acceptance transitions.


### Startup network preflight

`preflight`: `{ "network":"restricted|allowed|unknown", "channel":"actual host execution channel" }`. Returns ready or an actionable failure, elapsed time and an artifact reference. Known restricted networking performs zero requests. Otherwise it validates credentials and a fixed synthetic Jev choice with one request attempt and a ten-second timeout. Run before the first network operation using the same permitted execution boundary as later Jev/pi calls. No project content is included, no permission is granted, and no global setting is changed. `doctor` remains a local check; it does not prove network connectivity. An existing run is optional: the supplied run-id provides the diagnostic/artifact location.


### Host actions and diagnostic export

`host-action` records an immutable, local host observation even before run initialization or after an API failure:

```json
{"actionId":"review-attempt-1","sessionId":"host-session-1","kind":"review","phase":"planned","summary":"Request fresh review of the current task","taskId":"layout","next":"Request host network permission"}
```

Kinds: decision, worker, review, edit, check, integration, permission, other. Phases: planned, permission-granted, permission-denied, started, completed, failed, skipped. Use the same action/session identifiers for an attempt's observations, and a fresh actionId for a retry. Summary is required; taskId and next are optional. Summaries should contain concise reasons and local evidence references, never credentials. Logs use existing best-effort secret masking; arbitrary sensitive text is not guaranteed to be detected.

`diagnose` includes this ledger and unreadable-record names alongside runtime diagnostics. These are host attestations, not proof of tool execution or authorization. Missing outcomes need reconciliation; an absent event does not prove the agent skipped a step. Same-timestamp records have no guaranteed causal ordering.

`diagnostic-export` writes a local JSON file under the run's exports directory and returns its path and content. Its structural allowlist excludes free text, prompts, code, original action/session/task IDs, model names, paths, raw tool output and exception messages. It retains pseudonymous action/session relationships, phase/kind, task status counts and runtime outcome/timing/usage summaries. It works without valid run state and reports unreadable record counts. The result still discloses operational metadata; inspect it before explicitly sharing. Nothing is automatically uploaded. Full explanations remain available locally through `diagnose`.

For legacy running claims only, `reconcile-execution` accepts `{id, operation, confirmedStopped:true, evidence}`. Copy the current owner operation exactly (omit when no owner exists). First verify that task execution has stopped, even if its coordinator process remains alive. This trusted host attestation archives the prior task and releases ownership into blocked state; it does not kill any process or remove files. Inspect preserved artifacts, then use `requeue` and route again. Never assert stopped while work is still executing.
