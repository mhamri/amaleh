# Command contract

Run `bun <skill>/scripts/cli.ts <operation> <workspace> <run-id> [input.json]` by default; fall back to `node <skill>/scripts/run.ts ...` only when Bun is absent, since modern Node directly executes the erasable TypeScript. Paths are arguments, not interpolated shell commands. There are no npm runtime dependencies.

Printing never changes what an operation returns. A machine caller always reads JSON, because JSON stays the default whenever stdout is not an interactive terminal. A person at a terminal instead gets a readable report — a headline answering the question, then aligned detail rows — from `doctor`, `list`, `status`, `health`, `next`, `diagnose` and `preflight`; every other operation pretty-prints its JSON. Pass `--json` to force the machine record even at a terminal. Human output is therefore opt-in by being a person at a terminal, never by guessing, and an existing caller that parses JSON is unaffected.

`doctor` takes no run; `list <workspace>` returns one summary per run — id, status, intent, acceptance criteria, task count, revision, the run it continues and its acceptance record — newest revision first. Read it before starting anything, because later work on an existing outcome continues that run rather than opening a new one. `install` links this canonical skill into the default Claude/Codex skill directories and refuses conflicting targets. Windows uses directory junctions; Unix uses directory symlinks. `uninstall` is the inverse and takes the same optional home argument: it removes only those two links, reports each target as `removed` or `not installed`, and refuses a real directory, a file or a link that resolves elsewhere with `Conflicting skill target: <target>` while removing nothing. It never deletes the checkout itself.

## Input examples and operations

`start`: `{ "host":{"kind":"codex","model":"actual model from session"},"intent":"requested outcome","criteria":["observable success"],"constraints":["accepted restriction"] }`. Add `"continues":"<prior run id>"` to build on earlier work: the new run inherits that run's acceptance criteria and every settled requirement decision, so an accepted palette, contract or interface is not decided again from zero. Without `continues`, an intent that substantially repeats an existing run is refused and the matching run is named; `"unrelated":"<reason>"` overrides when the word overlap is coincidental. Add `"shape":{...}` with the shape of the intent (see `shape` below). Without `shape`, `next` returns `shape` and `plan` refuses until the intent is shaped. In a Git checkout with a remote, `start` fetches that remote, resolves its default branch from the remote HEAD, and refuses unless HEAD contains the fetched tip; the refusal names the remote branch (for example `origin/main`) and the Git commands that fix it. Input `base.userInstruction`, quoting the user, overrides the refusal and is recorded with the quote. A workspace outside Git, or with no remote, records a `base-unverified` event with the reason and proceeds; a failed fetch refuses with the Git error unless `base.userInstruction` is given. Create each run branch from that fetched default branch, and keep merges in the run's integration worktree rather than the checkout the skill itself runs from. After that base verification and before the run exists, `start` makes the project ignore its own Amaleh folder: when the workspace is a Git work tree and `git check-ignore -q .amaleh/worktrees/probe` reports the path not ignored, it appends `/.amaleh/` to `<workspace>/.gitignore` (creating the file when it is missing, and adding a newline first when the file does not end with one) and commits only that path as `Ignore Amaleh run state and task worktrees`, leaving any other staged change staged. That commit is the run branch's first commit, so the task worktrees and the run state never show up in the project's diff. It refuses, naming `git switch -c <branch> <remote>/<default branch>` (or `git switch -c <branch>` when there is no remote), on a detached HEAD and on the remote default branch itself, because that commit must not land there; it refuses, naming `.gitignore`, while `.gitignore` has uncommitted changes, an untracked `.gitignore` included, because the commit must contain the ignore line alone. When the folder is already ignored, nothing is committed. A `worktree-folder` event records which happened: `{status:'committed',commit:<sha>}`, `{status:'ignored'}`, or `{status:'unverified',reason:<why>}` outside Git, where start proceeds as usual.

`feedback`: `{ "text":"the user's actual words" }` records user feedback as a new request. `next` then returns `shape`, and `plan`, `amend`, `invalidate` and `delegate` refuse until it is shaped. Record feedback the moment it arrives, even while a batch is running; running chunks finish, and nothing new starts on the old understanding.

`shape`: `{ "understanding":"what is asked and what it is for", "gaps":["..."], "pushback":["..."], "additions":["..."], "mentor":["reusable principle, only when warranted"], "options":[{"id":"headline","summary":"...","gains":"...","costs":"..."},{"id":"split","summary":"...","gains":"...","costs":"..."}], "recommendation":"headline", "questions":["..."], "affects":["hero"], "chosen":{"option":"headline","quote":"the user's words"} }` shapes the latest request. Pass two to four `options` with a `recommendation`, or `clearCut` naming why the request has only one sensible reading. `affects` names delivered tasks that feedback reshapes. A shape with `questions`, or with `options` and no `chosen`, stays open: `next` returns `ask-user` with the questions, options and recommendation, and the gated operations keep refusing. Run `shape` again once the user answers. `chosen` records a `requirement` decision with the user's quote as its reason. The full shape is archived as an artifact. Runs recorded before shaping existed carry no request and are not gated. See [shape every request](planning.md#shape-every-request).

`plan`: `{ "tasks":[{"id":"charge","title":"Correct charge","goal":"Apply the agreed amount rule","phase":"checkout","deps":[],"resources":["src/checkout/**"],"criteria":["expected totals hold"],"kind":"code","checks":[{"id":"test","command":"bun","args":["test","test/charge.test.js"],"role":"probe"}]}],"integrationChecks":[{"id":"all","command":"bun","args":["test"]}] }`. Commands use executable plus argument arrays. Every check requires a `role`: `"probe"` detects the task's defect on the unchanged checkout; `"guard"` protects existing behaviour and is not subject to the probe pre-check. A code task must have at least one probe check, or a `"noProbe"` string explaining why no executable can detect the defect; `plan` refuses otherwise. These role rules, and the reserved `scope` id, apply to contracts written through `plan`, `amend`, `review-check` and `invalidate`; a run saved before they existed still loads and runs, and its checks without a role are never probe-gated. Integration checks carry no role. Resources are path globs relative to the task workspace, for example `"amaleh/scripts/adapters.ts"`, `"website/src/**"` or `"*"` for the whole workspace; a resource without a wildcard also owns everything under it. After every worker run the built-in `scope` check compares the changed and untracked paths of the task's Git diff against these globs and fails the chunk when a path matches none of them, so name the paths the task may actually touch. The id `scope` is reserved for that built-in check, so no task check may register it. Register actual project checks, not invented test commands. Research and plan tasks may have no executable checks but still need reviewed evidence. Plans may add tasks, not discard history or silently rewrite existing contracts. A task may carry `"skills":["installed-skill-name"]` and `"references":["path/to/design-contract.md"]`; the runtime reads those files at launch and inlines them into the worker's prompt, so name a skill instead of retyping its content into a brief. A bare name resolves to `SKILL.md` under the host's skills directory, a path resolves against the task workspace, and an unreadable entry fails the launch naming every path tried. One task per independently deliverable outcome: a single task carrying three or more run outcomes, or four or more of its own criteria, is refused because nothing in it can run in parallel. `"singleChunk":"<reason>"` overrides when the work genuinely cannot be divided, and the reason is recorded.

`amend`: `{ "id":"charge","reason":"actual changed requirement or diagnosis","task":{...complete updated task contract...} }` deliberately changes an existing contract while retaining identity and escalation ancestry, invalidating affected descendants, and validating the updated graph. Do not create a replacement ID merely to reset repair history. An amend spends a repair cycle only when the task is in `review` with a failing check other than `scope`, or with an open blocking finding, because only then is the next worker run a repair; the descendants it reopens spend none. An amend that changes nothing but `resources` on a task holding a finished output (in `review`, or host work returned by `host-checks-failed`) with no open blocking finding keeps that output and leaves the task in `review`, so the next `delegate` re-runs checks, `scope` and review with no new worker run. An amend answers a pending scope question: any out-of-scope path the new resources still leave out is reverted by a repair. An amend also answers an open contract question (see `delegate`), and then spends no repair cycle; when it changes nothing but `checks` or `resources` on a task holding a finished output with no open blocking finding, it keeps that output in `review`, so the next `delegate` verifies it against the corrected contract with no new worker run. The `contract-amended` event records `keepsOutput`, `charged` and `answersQuestion`. Descendants of the amended task are sent back as `invalidate` describes: an accepted one keeps its output for verification. Add `"feedback":true` when the amendment delivers shaped user feedback that names this task in `affects`; the reopen then spends no repair cycle. Each task can be reopened once per feedback. `amend` records its reopen as a contract reopen and `invalidate` as a defect reopen: the reopen health warning and `metrics.reopenedChunks` count only defect reopens, so an amendment that only changes a task contract is not reported as a defect the checks missed. Feedback reopens are recorded separately and stay uncounted. An amend that asks an accepted task for more is the exception; see [reopening accepted work](#reopening-accepted-work).

`next`, `status`, `resume`, `html`: no input. `status` includes durable references and phase status. `html` returns a local HTML progress artifact.

On a new host/model, pass `resume` an input with `host: {kind, model}` containing the actual current coordinator. The handoff retains the prior identity in history and allows escalation to the current host. Completed runs resume as `done` without mutation.

`effort-configure`, `effort-request`, `effort-start`, `effort-finish`, `effort-reconcile` implement the conditional same-model effort path; see [effort](effort.md) for validated input shapes and host execution requirements. `next` exposes requested/running passes and `status` preserves the baseline and execution receipt. A host/model switch must first reconcile any active effort pass.

`record-decision`: `{ "id":"intent-answer","question":"What outcome?","answer":"The user's actual answer","source":"user","reason":"Reference to the actual instruction" }` records settled intent without a Jev call. Use source `host` only for delegated technical decisions. Never invent a user answer. `block` accepts an optional task `id` to block only that task and its dependents while unrelated work proceeds.

`pools`: `{ "pools":[{"role":"frontend","models":["verified exact model IDs"],"requiredInputs":["text","image"],"requiresTools":true,"notes":"User preference and relevant evidence"}] }` persists purpose-specific routing preferences. Filter these against current catalog capability facts before dispatch; configuring a model does not prove eligibility.

`decide`: `{ "id":"unique-decision","question":"Which route is justified?","criteria":{"source":"Read relevant code","execute":"Evidence is sufficient"},"state":{"task":"...","facts":["..."]} }`. Use actual evidence, not empty routing ceremony. Response chooses an option or yields `host-decision`. OpenRouter Jev uses the decisions endpoint, not chat completions. `host-decision`: `{ "id":"unique-decision","choice":"source","reason":"evidence and reasoning" }`.

`decide-batch`: `{ "decisions":[{ "id":"...", "question":"...", "criteria":{...}, "state":{...} }, ...] }` settles up to sixteen independent questions in ONE gateway call and one input file. Always prefer it over repeated `decide` calls when more than one question is open; each answer is recorded individually and low-confidence entries still yield `host-decision`.

`delegate`: `{ "id":"charge", "workspace":"absolute task workspace", "brief":"optional extra guidance", "lenses":["optional review lenses"] }` hands a whole chunk to the runtime. Before the first worker launch, it runs every probe check on the unchanged checkout; a probe that passes there cannot detect the task defect, so the chunk is refused, naming the passing probe. This pre-check only applies before the first worker run: a task whose delivered output shaped feedback reopened carries that output, so its probes are not re-gated and the reopened chunk delegates normally. It then routes and launches the worker (round-robin), assembles the brief from the task contract when omitted (see [the worker's share of the run](#the-workers-share-of-the-run)), runs registered checks (a check that fails is run again alone before it counts; see [check isolation](#check-isolation)), obtains independent other-family review, asks [the Jev gate](review.md#the-jev-gate) before each repair, and drives repair cycles up [the repair ladder](#the-repair-ladder) (Flash → Kimi → host) autonomously. The review after a repair continues the first reviewer's session and reads only the repair; see [the review after a repair](review.md#the-review-after-a-repair). Every outcome lists the findings the gate settled as `settledFindings`, each `{verdict, finding, owner?}`. Host work is final: when the host itself wrote the result under `host-exception`, `delegate` runs the registered checks and `scope` and accepts with no model review, reporting `hostFinal:true`; when one fails, it returns `escalated` with stage `host-checks-failed`, puts the task back in `repair` and spends no repair cycle. A task at host depth that has no finished host result returns `escalated` with stage `host-takeover` and the host model, without routing. One coordinator invocation per chunk. A task left in `review` with a recorded result and no live owner, for example after its review failed on a provider error, is delegated again straight to checks and review; the finished worker output is reused, not bought again. The same holds for an accepted dependent that a reopen of its upstream sent back to `review`; until its dependencies are accepted and integrated again, `delegate` returns `route-pending` with a `dispatch-blocked` route naming them instead of verifying it early. Such a dependent is judged in its own checkout, so that checkout must contain the upstream it depends on: while the run's main checkout HEAD is not an ancestor of the dependent checkout's HEAD, `delegate` returns `escalated` with stage `refresh-checkout`, naming the missing commit, and `next` returns `refresh-checkout`. Merge the run branch into that checkout and delegate again. A checkout outside Git cannot be compared and is verified as it stands. A `brief` given to `delegate` also reaches every repair worker the call starts, as coordinator guidance. A worker that finds the task contract itself wrong (a registered check that cannot pass for a reason outside the task, criteria that contradict each other, or vendor code it would have to write without a source) raises a contract question through the bundled helper instead of working around it, and finishes its run. Before any check runs, because the question may be about one of them, `delegate` returns `escalated` with stage `contract-question`, the `questions` and the worker's output artifact as `workerOutput`; it spends no repair cycle and no model reviews that output. `next` returns `contract-question` until it is answered. Either `amend` the contract (recorded as a `contract-answered` event with answer `amend` and the amendment's reason), or delegate again with a `brief` that says why the contract stands (answer `stands`, with the brief as its reason): the checks and review then judge the output as it stands, and the brief reaches any repair worker. `delegate` refuses a task with an open contract question when no `brief` is given, and one answer closes every open question on the task. After each worker run, and again after every repair like the registered checks, the built-in `scope` check compares the changed and untracked paths of the task's Git diff with the task's resource globs: any path matching no resource is a failing `scope` receipt whose output lists every out-of-scope path. A failing `scope` check does not start a repair: `delegate` returns `escalated` with stage `scope-question`, `outOfScope` and the worker's output artifact as `workerOutput`, spends no repair cycle, and `next` returns `scope-question` until it is answered. `amend` the task's `resources` to keep the paths, and the next `delegate` verifies the same output with no new worker run; or delegate again, and a repair that spends a cycle reverts them. The `scope-question` event is saved in the same state revision as the failing `scope` receipt, and the answer is recorded as a `scope-answered` event: `revert` when the next `delegate` starts, `amend` when an amendment arrives. Each path is asked about once per task: a later run that keeps a path already asked about is a failed repair and spends a cycle, and only a path nobody was asked about raises a new question. An unchanged checkout keeps its `scope` receipt when the task is delegated again, like the registered checks. `result` drops the review of the output it replaces. `scope` is reserved for this built-in check, so no task check may register it. A workspace outside Git has no diff; the check then records a `scope-unverified` event saying it could not run rather than passing silently. A review that leaves coverage debt without a blocking finding is retried once by a fresh reviewer from another eligible family — not the author's family and not the family that left the gap — and is accepted if that review is complete; only a second gap escalates. In the reviewer stage, any reviewer call failure other than a workspace escape or a settled funding or authorization failure is replaced by a new review on a model whose family did not fail, bounded by `providerFailovers`, and recorded as a `provider-failover` trail stage and event with stage `reviewer`; when that budget runs out, `delegate` returns `failed` and the task stays in review with its worker output. Worker-stage failover replaces a transient provider failure, and a worker call the runtime stopped before it changed anything; see [worker failover](#worker-failover). Outcomes: `accepted` (chunk done, integrate next; it carries `unstableChecks` when a check failed only beside other checks), `escalated` (repair-exhausted/host-takeover/host-checks-failed/scope-question/contract-question/review-evidence/workspace-escape — your turn to diagnose, answer, supply evidence or restore files), `route-pending` (resolve the named prerequisite), `refused` (a probe already passes on the unchanged checkout), `failed` (infrastructure error; task state preserved). A `trail` records each stage, including every `scope` verdict. Do not call `worker`/`check`/`reviewer`/`repair` manually for a delegated chunk. `delegate` also accepts `skills` and `references`, which override the task's own for this chunk.

`delegate-batch`: `{ "ids":["hero","docs","pricing"], "briefs":{"hero":"optional extra guidance for this chunk only"}, "lenses":["optional review lenses"], "skills":["optional shared skill"], "references":["optional shared contract"] }` delegates every ready chunk in one invocation, bounded by `maxWorkers`, starting the next id the moment a slot frees. Use it for one chunk too; a sequence of single `delegate` calls wastes the capacity that is already configured. Each task needs its own isolated checkout, so omit `workspace` and let each id use the workspace recorded on its task. Passing one shared `workspace`, or two tasks pointing at the same checkout, is refused before any worker starts — concurrent tasks in one checkout serialize into conflicts rather than into parallel work. Two batched tasks whose `resources` overlap never run at once: the batch holds the later one and starts it the moment the earlier one finishes, while tasks with separate resources keep running alongside. Overlap is judged conservatively: two resources overlap when the directory one of them matches under contains the other's, so `website/src/**` overlaps `website/src/lib/x.ts` and `**/*.md` overlaps everything, while `website/src/**` and `website/scripts/**` do not. Paths are compared ignoring case, backslashes, `./` and repeated slashes, and a resource containing `..` overlaps everything. The same rule decides conflicts with live tasks outside the batch, which routing reports as `dispatch-blocked` and `claim` refuses. A `briefs` key that is not in `ids` is refused. The CLI runs the batch in a detached process, because a batch lasts far longer than any host tool call. It returns `{launched, pid, ids, cursor, log}` as soon as the batch has recorded its first chunk. The detached process writes its final `{delegated, concurrency, outcomes}` report to `log`. A batch that fails before starting any chunk is reported as an error carrying the tail of that log. `"foreground":true` runs the batch inside the calling process instead and returns the outcomes directly; use it only from a script that can block for the whole batch.

`worktree`: `{ "id":"charge", "base":"<optional commit-ish>" }` creates the task's isolated checkout inside the project, at `<workspace>/.amaleh/worktrees/<run-id>/<task-id>`, with `git worktree add -b amaleh/<run-id>/<task-id> <path> <base>`; `base` defaults to the HEAD commit of the run's own checkout, and when the branch already exists it checks that branch out instead of creating it. It records the path as the task's `workspace` and a `worktree-created` event `{id,path,branch,base,created}`, and returns `{ "id", "workspace":"<absolute path>", "branch", "base":"<commit sha>", "created":true|false }`. Calling it again for a task whose registered workspace is that path changes nothing and returns `created:false`. It installs no dependencies, so a worktree that needs them still needs the project's own install step. It refuses outside Git, refuses while `.amaleh/worktrees/` is not ignored — naming the `start` commit that makes the project ignore it — and refuses a task that is already running or accepted, because that task keeps the checkout it has, and refuses a task that holds output in a different checkout, because a new worktree would not contain that output. Task worktrees therefore live in the project, never in a sibling folder, and every path a task writes stays inside its own checkout while the run state stays outside it.

`worktrees <workspace>` takes no run and lists every worktree of the project's repository: `{ "defaultBranch":"origin/main"|null, "worktrees":[{ "path", "branch"|null, "head", "main":boolean, "dirty":boolean, "adds":boolean|null, "mergedVia"?:string, "missing":boolean, "task":{"run","id","status","integrated":boolean}|null }] }`. `main` marks the main working tree, `dirty` is true when `git status --porcelain` in that worktree is not empty, and `missing` marks a worktree Git still lists whose directory is gone. `adds` answers whether that worktree's branch still adds anything to the freshly fetched default branch: it compares the tree `git merge-tree --write-tree <default tip> <head>` writes with the default tip's own tree, so a squash-merged branch reads `false` even though its commits are not ancestors, a real change reads `true`, and a merge conflict reads `true` as well. A branch that reads `true` is then checked against every other local and remote-tracking branch that contains its head commit: when one of them adds nothing to the default tip, the branch's work reached the default branch through it, so `adds` becomes `false` and `mergedVia` names that branch. This covers a task branch whose run branch was squash-merged after a later task rewrote the same lines, which conflicts with the default branch on its own. Without a remote it is `null` with a `reason`. `task` names the run and task whose recorded workspace is that path, which is what tells an old worktree apart from a live one.

`clean-worktrees <workspace>` with `{ "paths":["<absolute path>"], "userInstruction":"<the user's words>", "deleteBranches":true|false }` removes old worktrees, and never one without `userInstruction`: a missing or empty quote is refused. It refuses, removing nothing, when a named path is not a worktree of the repository, is the main working tree, is dirty, or is the workspace of a task in a run that is not complete and whose task has no `integrated` record; every problem is listed in one refusal, so a partly valid request changes nothing. Each worktree is then removed with `git worktree remove <path>`, never with `--force`, and the empty folders it leaves under `.amaleh/worktrees` are removed with it; a worktree whose directory is already gone is pruned from Git rather than refused. With `deleteBranches`, a removed worktree's branch is deleted only when `adds` was `false`, including through `mergedVia`, so a branch that still carries work survives. The result is `{ "removed":[{ "path", "branch", "branchDeleted":boolean }] }`.

`drive`: `{ "briefs":{"hero":"optional extra guidance for this chunk only"}, "lenses":["optional review lenses"], "skills":["optional shared skill"], "references":["optional shared contract"] }`, or no input file at all, runs the whole run until the main model is needed; see [drive](execution.md#drive). Like `delegate-batch`, the CLI runs it in a detached process and returns `{launched, pid, cursor, log, follow}` as soon as the `drive-started` event exists; `"foreground":true` runs it inside the calling process and returns the report directly. The report is `{outcome, accepted, integrated, handedBack, failure?}`: `outcome` is `ready-to-verify` when every task is accepted and integrated, otherwise `host-needed`; `accepted` holds each accepted chunk's `delegate` outcome without its `trail`; `integrated` lists the task ids `drive` merged; `handedBack` holds one entry per task the main model must look at — a `delegate` outcome that is not `accepted`, or `{task, outcome:"integration-needed", stage, reason, files?}` for a merge `drive` could not make. The report is saved as an artifact and named in the `drive-finished` event `{outcome, report}`. One run has one live drive: a second `drive` is refused while the first one's process is alive. `resume` closes a drive whose process is gone with `drive-finished {outcome:"interrupted"}`.

`wait`: `{ "after":<cursor>, "until":"drive", "timeoutMs":100000 }` follows a drive. It returns when a `drive-finished` event exists after `after`, when no live drive exists, or when `timeoutMs` passes. The result is `{outcome, cursor, drive, live, next}`: `outcome` is `finished` (with the report as `drive`), `interrupted` (the drive's process is gone; run `resume`), `still-running` (call `wait` again with the same `after`) or `idle` (no drive ran after `after`). `live` names the chunks still running.

`wait`: `{ "after":<cursor>, "timeoutMs":100000 }` follows running delegations. It returns as soon as a chunk has finished after `after`, a delegation's process is gone, no delegation is running, or `timeoutMs` passes. The result is `{outcome, cursor, finished, live, interrupted, next}`. `outcome` is `finished`, `interrupted`, `idle` or `still-running`. `finished` lists `{id, outcome, reason, at}` for each chunk that finished after `after`, including a chunk refused before it started. Pass the returned `cursor` as `after` on the next call, so no outcome is reported twice or missed. Without `after`, it waits for the next finish from now on. `interrupted` names delegations whose recorded process no longer runs on this host; `resume` closes them and blocks their tasks for reconciliation. `timeoutMs` is 100000 by default and 540000 at most; set it just under the host's tool timeout. `wait` only reads state, so polling it adds no revisions.

Workers consult Jev mid-task without the coordinator through the bundled helper: `node <skill>/scripts/jev.ts <workspace> <run-id> <task-id> "<question>" "<optionA>|<optionB>|..."`. Worker briefs include this automatically; calls are recorded as `worker-jev` events. The helper sends Jev the task contract as its state — the run intent and constraints, and the task's id, goal, criteria, resources, kind, check ids with their roles, and repair cycles spent — so Jev judges the options against what the task must do; a sixth argument the worker passes arrives as `workerState`. The delegate loop's [Jev gate](review.md#the-jev-gate) sends the same contract with the blocking findings, the failing checks, the other tasks' resources and the cause of the previous repair.

Workers raise a contract question through the second bundled helper: `node <skill>/scripts/question.ts <run workspace> <run-id> <task-id> "<what is wrong, with the evidence>" [check-id]`. It records a `contract-question` event while the task's worker runs, refuses a check id the task does not have, and tells the worker to stop working on that part and finish its run. Jev chooses between options inside the contract; the question helper is for a contract that is itself wrong.

`catalog`: fetches dated candidate cards including capability, price, and source. Select stable eligible models and record exact IDs; the description is not local performance proof. Set `AMALEH_JEV_MODEL` to a verified current OpenRouter Jev ID if the installed default becomes stale.

`claim`: `{ "id":"charge","workspace":"absolute task workspace","model":"actual selected model","routeDecisionId":"decisionId returned by route" }`. A fresh matching worker route is required and consumed atomically; an arbitrary model name is insufficient. For direct host exceptions, first call `host-exception` with `{ "id":"charge","reason":"user-request","evidence":"actual explicit user instruction" }` or reason `repair-escalation` after the persistent repair allowance is exhausted. Pass the returned `authorization` as `hostAuthorization` instead of `routeDecisionId`, with the actual host model. Grants are single-use and scope-bound. `worker` takes `{id, workspace, brief, routing?}` and selects a model automatically before it invokes pi, records real model/session output and checkpoints the result. Never concurrently run workers in the same checkout. `result`: `{ "id":"charge","output":{"changes":["..."],"remaining":[]} }`.

`check`: `{ "id":"charge","checkId":"test" }`; omit `id` for a feature integration check. Runs the registered executable under the shared check lock (see [check isolation](#check-isolation)), saves output and fingerprints. If a check changes files, rerun checks invalidated by those changes before acceptance.

`reviewer`: `{ "id":"charge","lenses":["Spec","Standards","money path"],"routing":{"evidence":"Relevant suitability evidence"} }` invokes a fresh read-only pi review. Its prompt asks the reviewer to report every blocking defect it can find in this one pass rather than stopping at the first, while grouping lenses that describe one root defect into a single finding. A reply that is not a valid report is re-requested once with the exact rejection reason, in the reviewer's own pi session (`--continue` against a `--session-dir` unique to that review), so the inspection it already paid for is kept. The review and its correction are one speed sample, with their elapsed time and output tokens added together; a review that never returns a valid report is recorded as failed. `review` records a review obtained through a supported native agent instead: `{ "id":"charge","model":"actual reviewer model","fingerprint":"from fingerprint operation","report":"coverage and findings evidence","findings":[] }`. Never fabricate a reviewer identity or report. Findings require id, lens, location, scenario, evidence, consequence and a boolean blocking field.

`repair`, `accept`: `{ "id":"charge" }`. Repair updates the persistent escalation counter and picks the depth of the next worker; see [the repair ladder](#the-repair-ladder). `integrated`: `{ "id":"charge","evidence":"actual integration and interaction inspection evidence" }` after the host integrates changes and checks compatibility. It compares the task's checkout with the accepted output, so record it before removing the task's worktree: once the checkout is gone it refuses, naming the missing path. `finish`: `{ "claims":["evidence explanation corresponding to each run criterion"] }` after all tasks integrated, full required checks pass and Jev claim-support decisions resolved. While a task is not accepted and integrated, `finish` refuses with `Incomplete tasks:` followed by each such task and its state. A finished run cannot change: any operation that would write to it refuses and names the `"continues":"<run id>"` input that starts a new run on its criteria and settled decisions. Before closing, `finish` fetches the remote default branch again and refuses while merging it into HEAD would conflict, naming the conflicting files; a workspace outside Git or with no remote is skipped with an event. These host attestations are trusted operator input, not cryptographic proof of correctness. `finish` refuses while `health` reports delegation warnings, listing each one; `"acknowledgeWarnings":"<reason>"` overrides and records a durable `health-acknowledged` event in the same revision as the finish, so a failed finish leaves no acknowledgement behind. A run that did the work by hand therefore cannot close silently.

`save`: archives any JSON evidence; returns a content ID. `artifact`: `{ "id":"artifact hash" }` retrieves original evidence. `fingerprint`: optional `{ "workspace":"task checkout" }` returns exact current content fingerprint.

`block`: `{ "reason":"external failure and intervention needed" }`. `requeue`: `{ "id":"task","evidence":"interrupted effects inspected and reconciled" }` only for blocked tasks. `invalidate`: `{ "id":"task","reason":"which accepted assumption/evidence changed" }`; repair ancestry remains. `configure` accepts positive integers for maxWorkers, flashRepairCycles, deepRepairCycles. `maxWorkers` changes freely. The repair budget is the user's policy: changing `flashRepairCycles` or `deepRepairCycles` needs `"userInstruction"` quoting the user's explicit request, which the `configured` event records. Resubmitting the current values needs none. `invalidate` counts as a repair cycle for the task it names when that task already produced output, so a reopen spends the same budget as an in-loop repair. Only that task carries the defect. Every task that depends on it is sent back too. One that was accepted, or awaiting review with no failing check and no open blocking finding, keeps its output in `review` and spends nothing: once its dependencies are accepted and integrated again and its checkout contains them, `delegate` checks and reviews it with no worker run. One whose own last attempt failed returns to `ready` and spends a cycle, because its next worker run repairs that failure; one with no output returns to `ready` and spends nothing. Feedback reopens charge nobody. The `invalidated` event lists the kept dependents as `reverified`. Reopening such a task also needs the probe that found the defect: `"check":{"id":"rendered","command":"node","args":["scripts/check-rendered.mjs"],"role":"probe"}` joins the task's checks, so every later repair of the task runs it inside the chunk loop. A check with role `probe` must fail on the task's own checkout before the reopen is recorded; a probe that passes there cannot detect the task defect, so the reopen is refused. Every other rejection of the request is decided before that probe runs, so an invalid request never executes the supplied command. A `guard` check is registered without this pre-check. Passing the same check again is accepted; a different command under an existing check id is refused. When no executable can show the defect, pass `"noProbe":"<why>"` instead. `noProbe` is accepted once per task: a second defect the checks cannot see means the checks are missing something, so the second reopen needs `check`. `"feedback":true` reopens a task named in the `affects` of the latest settled feedback shape; it needs no probe and spends no repair cycle, once per task per feedback. `unlock` verifies a dead same-host lock owner before removing a stale lock; never delete a live or unverifiable lock.

### Reopening accepted work

An `amend` without feedback that asks an accepted task for more — a new `goal`, changed `criteria`, or a check id the task did not have — reopens delivered work that its checks and review already passed. That is the same event as a defect `invalidate`: the host found something the accepted checks missed. So it follows the same rules. It needs the probe that shows the gap, added to `task.checks` with role `probe`, and every new probe must fail on the task's checkout before the amend is recorded; a probe that passes there is refused. When no executable can show the gap, pass `"noProbe":"<why>"` next to `task` instead, once per task, shared with `invalidate`'s `noProbe` allowance. The reopen is recorded as a defect reopen, so it counts in `metrics.reopenedChunks`, and it spends a repair cycle on the task, because the next worker run repairs delivered work. The `contract-amended` event carries `reopenedAccepted:true` and a `reopen-probe` event names each new probe. An amend of an accepted task that changes only `resources`, `title`, `phase`, `deps` or `kind`, or only removes checks, asks for nothing more: it stays a contract reopen, needs no probe and spends no cycle. A change the user asked for is feedback: record it with `feedback`, shape it, and amend with `"feedback":true`, which needs no probe and is never counted. Split a defect and a contract change the other way round too: `invalidate` the defect with its probe first, then `amend` the task, which is then no longer accepted.

### The repair ladder

A task in repair has a depth: `flash` (a cheap Flash model repairs it), `deep` (a `deep` model from `models.json`, Kimi by default) or `host` (the main model takes over under `host-exception`). Each `repair` spends one cycle and picks the depth from two things: how many cycles the task has spent, and whether the last repair removed the defect it was given.

- By count: the first `flashRepairCycles` repairs run at `flash`, the next `deepRepairCycles` at `deep`, and after that the task is at `host`.
- By evidence: when [the Jev gate](review.md#the-jev-gate) answers that a defect of the previous round is still there, the next repair runs at `deep` at once, even when Flash cycles remain. A second Flash attempt at a defect Flash just failed to remove is the most likely cycle to be wasted. When the repair that failed was itself a `deep` one, the task goes to `host` at once: the outcome is `escalated` with stage `repair-exhausted` and the reason "The same defect survived a deep repair".
- New defects each round stay at `flash` until the Flash allowance is spent. Kimi is therefore bought for a defect that resists, not for a chunk that is merely long.

The total never exceeds `flashRepairCycles + deepRepairCycles` repairs before `host`, and the deep model never runs more than `deepRepairCycles` times in one ladder. Reopening an accepted task with `invalidate`, or with an `amend` that asks for more, starts a new ladder at `flash`: the reopen still spends a cycle and `cycles` keeps counting for the task's whole life, but the new defect is a different defect, so it starts on the cheap model. `host-exception` with reason `repair-escalation` needs a task at `host` depth that reached it through the ladder.

Each `repair` event carries `{id, cycle, depth, cause, sameDefect?}`. `cause` is `{failingChecks, findings}`: the ids of the checks that failed and, for each open blocking finding, its `id`, `lens`, `location` and `scenario`. `health` adds these up in `metrics.repairCauses`: `afterFailedCheck`, `afterReview`, `notRecorded` (repairs recorded before causes existed), `sameDefectAgain` and `byCheck`. `metrics.firstPassAccepted` counts the tasks accepted with no repair at all.

### Main model usage

The main model is the largest cost the run cannot see from OpenRouter: every turn it takes reads its whole conversation again. For a Claude Code host, `health` measures it from the session transcripts under `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<the workspace path with every character that is not a letter or digit replaced by a hyphen>/`, sub-agent transcripts included; `AMALEH_HOST_TRANSCRIPTS` names another folder. It counts every assistant message between the run's first event and now (the run's last event, once the run is complete), once per message id: `metrics.mainModel` is `{available:true, source, turns, toolCalls, inputTokens, cacheReadTokens, cacheWriteTokens, outputTokens}`. The figure is tokens, not money, because the transcript carries no price. It is attributed by time: every Claude session that worked in that workspace inside the window counts, so two runs that were active at the same time each report the sum. For any other host, or when the folder holds no turn of this run, it is `{available:false, reason}`; unknown is not zero.

`health` warns when the main model read more tokens (new input, cache reads and cache writes together) than every worker and reviewer of the run together. The cure is fewer main-model turns, so the warning names [drive](execution.md#drive). It blocks `finish` like the other warnings.

### Check isolation

Chunks run their checks on one machine. Several test suites running at once can push a timing-tight test past its limit, and that failure says nothing about the task. So every `check` takes a lock under `.amaleh/check-lock` before it runs. A normal run takes it shared, so normal runs still run side by side. An isolated run takes it exclusive: it waits until every shared run has finished, and no new shared run starts until it is done. Inside `delegate`, a registered check that fails is run once more, isolated, before the failure counts. When the isolated run passes on the same content fingerprint, the runtime records a `check-unstable` event with the task, the check id, the fingerprint and the receipts of both runs, and the chunk goes on to review without spending a repair cycle. When the isolated run fails too, its receipt stands and the normal repair path follows. When the failed run changed the content, the isolated run judges the new content like any later run of that check, and no `check-unstable` event is recorded, because the pass does not show that load caused the failure. A receipt from an isolated run carries `isolated:true`, and a current isolated receipt is not run a third time. The review packet gives such a check `unstable.failedOutput`, the end of the failed run, and asks the reviewer whether the task's change causes that failure — a race, a shared file or port, a timing dependency the change added — and to file a blocking regression if it does. An `accepted` outcome lists those checks in `unstableChecks`, and `health` counts `check-unstable` events in `metrics.unstableChecks`, shown as "Checks failing only under load". Of two isolated runs that meet, the one registered with the earlier name goes first, and the other withdraws until it is done. Each holder refreshes its file every 5 seconds. The next check that finds a holder file removes it when its process is gone on this host, or when the file has not been refreshed for 60 seconds; the second rule covers a crashed holder whose process id is in use again and a holder on another host. A waiter whose own scans were more than 10 seconds apart, as happens to every process while the machine sleeps, skips the age rule on that scan, so a holder whose heartbeat is late for the same reason keeps its file. A holder file that cannot be read counts as held until it goes stale.

### Worker failover

The wall-clock limit, the idle limit, the reviewer turn limit and the debugger-wait guard stop a pi call from outside. Each such stop fails the call with a `CallStopped` error that names its trace stage: `call-timeout`, `idle-timeout`, `turn-limit` or `debugger-wait`. Inside `delegate`, a stopped worker call that left the task workspace's tracked content as it was lost nothing, so it is handled like a transient provider failure. Tracked content is the `HEAD` commit, the output of `git diff HEAD`, and every untracked file Git does not ignore, with an untracked symbolic link counted by its target path; outside Git it is the content fingerprint. Ignored build output and caches therefore do not count as a change. The task gets back the status it held, no repair cycle is spent, a `provider-failover` event and trail stage record the reason and the `excludedFamily`, and the worker is routed again with that model's family excluded. The exclusion lasts for the rest of the `delegate` call, repair workers included. A stopped call that changed tracked content is not retried: `delegate` returns `failed`, the task stays blocked with the reason, and the host decides what to keep. Both cases share the `providerFailovers` budget with transient provider failures.

### The worker's share of the run

The worker's brief, `sessions/<task>/brief.md`, carries the task packet. Its `task.criteria` and `task.checks` are the worker's contract. The run's acceptance criteria appear as `runOutcomes`: what the whole run must achieve once every task is done. They are background, not a checklist. `otherTasks` lists every other task with its `goal`, `resources` and `status`. When the run has more than one task, the brief adds a "Your share of the run" section that says the same in words: leave other tasks' resources to their owners, do not run a suite or edit a file only because a run outcome names it, and raise a contract question when the task's criteria cannot be met without changing another task's resources. The default brief asks the worker to satisfy every criterion in `task.criteria` and make every check in `task.checks` pass. The run-level packet that `status` and `diagnose` return still reports the run's criteria as `criteria`.

## Authentication and process settings

Use `OPENROUTER_API_KEY`, or pi's existing OpenRouter credential. The runtime never prints or writes it into artifacts. Expired pi credentials require refresh through pi. `AMALEH_PI_ENTRY` can name the installed pi JavaScript entry; the runtime picks the executable that runs it by resolving `AMALEH_RUNTIME` if set, otherwise `AMALEH_NODE` if set, otherwise `bun` found on PATH, otherwise the executable currently running the CLI. `AMALEH_NODE` is kept for existing configurations. Platform discovery checks common executable-adjacent global package locations without running shell shims. Worker calls disable external skills/extensions/context discovery; name the skills and reference files on the task instead, and the runtime hands the worker a file to read. The brief, the run context, any guidance and the reviewer's packet are all written to `sessions/<task>/` and referenced by path: a command line cannot carry them, and a file keeps the worker's own tokens paying for what it reads. A launch whose prompt still exceeds the limit is refused with the character count rather than an operating-system error. A worker that produces no output at all for `idleTimeoutMs` is treated as hung: its whole process tree is killed, the trace records an `idle-timeout` stage naming the last tool it started, and the chunk fails with that reason instead of holding a worker slot indefinitely. Set `idleTimeoutMs` to `0` to disable it. Independently of silence, every pi call stops at its wall-clock limit — `workerTimeoutMs` for a worker and `reviewerTimeoutMs` for a reviewer (defaults 2700000 and 2400000 ms, 45 and 40 minutes; `0` disables the limit). When a call passes its limit the runtime kills the whole process tree, records a `call-timeout` trace stage, and fails with a message containing 'time limit' without transient retry or length continuation. `delegate` routes a stopped worker to another family when the call changed nothing; see [worker failover](#worker-failover). A failed or timed-out call is written to the speed ledger with `failed:true` and its elapsed time, so it counts in `metrics.modelSpeed` and slow-model routing instead of disappearing. The worker prompt names the absolute task workspace and states that every edit and write must stay under it; the brief, the run's artifacts, the Jev helper, the contract question helper and the run's main checkout are named read-only. When the task workspace sits inside the run's main checkout, as it does for a worktree under `.amaleh/worktrees`, the prompt says so instead: only what lies outside the task workspace in that main checkout is read-only, and the brief and artifacts, which sit outside the task workspace as run records kept under that main checkout, stay read-only. It also forbids writing vendor code or setup for a third-party service from memory (copy it from a file in the workspace or the task's references, or raise a contract question), and requires every command to end on its own. A bash or powershell command that waits for a debugger forever is stopped at once: one whose segment launches `node`, `bun`, `deno` or `tsx` (directly, by path, or through `npx` or `bunx`) with `--inspect-brk` or `--inspect-wait`, or that assigns `NODE_OPTIONS` a value containing either flag. The runtime kills the worker's process tree, records a `debugger-wait` trace stage and fails the call with a message naming the flag, instead of waiting for `idleTimeoutMs`. A command that only mentions the flag, such as a search or an echo, is left alone, and a script that adds the flag itself is caught by `idleTimeoutMs` as before. Whichever limit stops a call first (debugger wait, turn limit, idle timeout or wall-clock limit) is the reason it reports. The runtime parses the path argument of every edit and write tool call in the worker's pi events and resolves it against the workspace. When a worker's edit or write targets a path outside the task workspace, the runtime kills the worker's process tree immediately and `delegate` returns `escalated` with stage `workspace-escape` naming every escaped path, without spending a repair cycle or provider failover. The task is left blocked with the escaped paths in its reason; the host is the only one allowed to restore files outside the task workspace, and requeues the task once they are restored. The guard sees only edit and write tool calls; bash and powershell side effects are invisible to it. A finished worker run is judged by what it changed, not by how it phrased its goodbye: a process that exits 0 with a complete `agent_end` but no final text is recorded as a result with an empty summary, and the registered checks and the reviewer decide whether the work stands. Reviewer calls still require final text, because the reviewer's reply is the JSON report it is judged by. A worker reply cut off by the model's output limit (`stopReason: length`) is continued once in the same pi session (`--continue` against the same `--session-dir`) with a short finish prompt; a second cut-off returns the partial reply so checks and review run on it. `error` and `aborted` stop reasons remain provider failures.

Model choice and runtime limits live in `amaleh/models.json`; `AMALEH_MODELS` points at a different file. Every field is validated, and a bad value names both the field and the file; `workerTimeoutMs`, `reviewerTimeoutMs` and `lightReviewLines` are optional and default when absent, so an existing configuration keeps loading. `flash` and `deep` are arrays of exact OpenRouter model ids — no wildcards and no family heuristics, so what runs is what you listed. Give `flash` at least two vendors: a reviewer must differ from the author's family, so a single-vendor pool leaves every task unreviewable the moment that vendor has a bad day. `jev` is the decision model, overridden per session by `AMALEH_JEV_MODEL`. `providerCooldownMs` is how long a model that exhausted its launch retries is skipped, `providerFailovers` how many times a chunk re-routes around a transient provider failure or a stopped worker call that changed nothing, `launchAttempts` how many times a single launch retries before giving up, `idleTimeoutMs` the silence that marks a worker hung, `workerTimeoutMs` and `reviewerTimeoutMs` the wall-clock limit for a worker and a reviewer call (defaults 2700000 and 2400000; 0 disables the limit), `reviewerMaxTurns` the most assistant turns a reviewer may take before it is stopped with a turn-limit failure (default 60), `lightReviewLines` the most changed lines a task may have for a light review (optional, default 200; 0 makes every review full; see [review effort](review.md#review-effort)), and `slowModelWindowMs` how far back routing looks for slow calls (default 604800000, seven days; 0 turns slow-model skipping off). 'Provider returned an empty response', 'Stream ended without finish_reason' and 'The model stopped before completing the response' count as transient provider failures, so both the launch retries and the chunk's `providerFailovers` route around them to another family; money, authorization and quota failures do not. They preserve pi's complete session messages and use the global configuration read-only in intent; pi may acquire its own configuration lock as part of startup.

## Diagnostic traces

`diagnose <workspace> <run-id>` returns current state, pending work, operation timelines, failures, unfinished operations and usage totals. It also works when initialization failed before a valid snapshot existed. Its `health` section (`health` operation standalone) measures delegation quality — coordinator-authored decisions per task, worker-side Jev calls, delegate vs manual dispatches, host-action ceremony, model-family distribution, contract questions (`metrics.contractQuestions`), checks that failed only beside other checks (`metrics.unstableChecks`; see [check isolation](#check-isolation)) and `metrics.coordinatorOperations`, the successful state-changing CLI operations the coordinator itself ran, which leaves out failed calls, the detached batch process (traced as `batch:delegate-batch`, and recognised in older runs as the `cli:delegate-batch` trace that starts while its launcher runs and outlives it) and read-only calls such as `health` and `fingerprint`. `metrics.revisions` is reported as a plain count with no allowance: most revisions are saved by the runtime inside `delegate`, three for every check it runs, so they measure the work, not the coordinator. Health emits warnings naming anti-patterns: coordinator micro-decisions, manual stepping through the worker→review→repair loop, decisions made at the wrong layer, excessive recording ceremony, single-family fixation, hand-made `worker`/`reviewer`/`repair`/`accept` calls outnumbering tasks alongside delegation, chunks reopened by a defect `invalidate` at least half as often as there are tasks (an `amend` that only changes a task contract, and a feedback reopen, are not counted), and one task carrying the whole feature. Use it to catch an expensive coordinator-driven run early; `finish` reads the same warnings and refuses on them. `metrics.hostTakeovers` counts every claim made under a `host-exception`, and `metrics.hostTakeoversByTask` splits that count by task; a takeover is an allowed boundary, not an anti-pattern, so it raises no warning. Every finished pi call, successful or failed, appends one line — start time, model, role (worker or reviewer), duration, output tokens and a `failed` marker — to `.amaleh/model-speed.jsonl`, shared by every run in the workspace. The first read of a missing file seeds it from the pi traces of every existing run. `metrics.modelSpeed` lists each model per role from the samples inside `slowModelWindowMs`: calls, a `failures` count, average and longest minutes per call, output tokens per second and output tokens per call; failed calls' elapsed time counts in the averages and the longest call, so a model that fails slowly is not hidden. `slowModels` names each model whose average call takes at least twice the median of its peers in that role, once that role has three peers with three or more calls each. A model's peers are the other models it competes with for the same route: the `flash` list in `models.json` for `health`, and the models configured for that route when routing. The model's own average is left out of its median, and a removed model or a `deep` model's short repair calls never lower it. Routing skips exactly these models for that role, so the report and the router always agree. A slow model is a vendor fact, not a coordinator mistake, so it never blocks `finish`; show it to the user. Trace files live in `.amaleh/runs/<id>/diagnostics`, independently of state commits; pi session paths and immutable artifact references remain available. API attempts record HTTP status, request identity when supplied, duration and usage. pi records process identity, tool progress, exit status and protocol/provider failures. An unfinished operation means active or interrupted; inspect ownership before replaying.

Costs are separated into OpenRouter response-reported cost, which Jev calls return, and estimated cost for pi worker and reviewer calls. pi's own estimate uses a local price table that lags the gateway: it prices a model it does not know at a default rate, so a free model can read as the most expensive one in the run. `health` therefore prices each pi call from the OpenRouter catalog card that routing recorded in the run's route decisions (`state.catalog.models[].pricing`), taking the card from the latest route recorded before the call started, because catalog prices change; a call that started before the model's first recorded route takes its earliest card. A negative or unreadable token count or pi cost in a usage row counts as zero. New input tokens cost the `prompt` rate, cache reads `input_cache_read`, cache writes `input_cache_write` (each falls back to `prompt` when the card has no rate of its own), output tokens `completion`, and every turn one `request`. A call whose model has no recorded card, or whose card carries a negative or missing rate, keeps pi's estimate. `metrics.spend` lists calls, turns, new input, cached and output tokens, `estimatedCost`, pi's figure as `piEstimate`, and `costSource` (`openrouter-catalog`, `pi-estimate`, or `mixed` when only some calls had a card) per model, per role and per task, plus one `total` row; the `diagnose` Cost line shows that total next to pi's figure. The catalog price is still an estimate, not a billed figure: OpenRouter can route a call to a provider that charges a different rate, so compare it with the OpenRouter activity page before quoting it. Totals count new input tokens and cached tokens separately (`cacheReadTokens`, `cacheWriteTokens`); a long worker call re-reads its whole context every turn, so cached tokens usually outnumber new input many times over. `health` warns when the `deep` models in `models.json` take more than 30% of an estimated spend of at least $0.10. That warning blocks `finish` like the others. Missing usage is unknown, not proof of zero cost. Telemetry redacts known credentials and sensitive fields, excludes prompts and tool bodies, and limits error text. Original authorized tool artifacts and pi sessions are separate and may include project content.

`next.parallel.ready` exposes independent dependency-ready candidates even while the focus action awaits review or repair. `parallel.available` reflects worker capacity; `claim` still enforces resource and workspace conflicts. Each `parallel.running` entry carries `alive`, and `parallel.delegations` lists open delegations with their process and `alive`. When no recorded owner of a running task or active verification is alive on this host, `next` returns `resume` instead of reporting that work as running. A pending decision may concern a candidate: satisfy its real prerequisites before dispatching.

`route`: `{ "id":"charge", "purpose":"worker", "workspace":"absolute checkout", "routing":{"role":"configured optional role","requiredInputs":["text"],"contextTokens":8000,"evidence":"Observed requirements and model suitability evidence"} }`. Purpose is worker or reviewer. Role is optional; omit it for default Flash pools. Selection is deterministic round-robin across eligible models, seeded by the run's session hash and advanced per routing decision inside the transaction that records it, so concurrently dispatched chunks alternate families instead of all selecting one model; no Jev call is spent on mechanical selection. A model that exhausted its launch retries on a transient provider failure is skipped for five minutes unless every candidate is cooling down. A model that `health` names slow for this purpose is skipped too, until its slow calls age out of `slowModelWindowMs`; it stays eligible when skipping it would leave no candidate. The routing decision records each skipped model under `skippedSlow`. `routing.excludeFamilies` is a hard filter for a reviewer, which must stay independent, and a soft one for a worker: a worker route skips those families unless that would leave no eligible model. A successful selection returns launch plus model and decision ID, without spawning. Selecting `reassess` or finding no eligible candidates returns `route-blocked`; revise the task/pool/evidence, then route again. Explicit model values on worker/reviewer must match the selected route and cannot bypass it. Legacy pending routes still resolve through `host-decision`.

`next.parallel.actions` lists each task's verification/repair/integration stage. `parallel.independent` suggests a conflict-free check/review batch bounded by available execution slots. Dispatch these through the host concurrently; they are not additional copies of the focus action. See [parallel execution](parallelism.md). Integration remains serial in the main workspace.


### Review coverage contract

`review-packet` input `{id,lenses?}` returns factual review context and exact required coverage IDs. Each check carries the last 3000 characters of its stdout and stderr. The pi `reviewer` also receives `changes`: the task's Git diff against the merge base of its checkout and the run's main checkout, limited to the task workspace, with a file summary and the list of new untracked files. The diff is taken against a snapshot of the checkout as it stands, so it holds the full content of every new file, tracked or not; a reviewer handed an empty diff for a new file has to search the checkout for what changed. The patch is a file in `sessions/<task>/`, cut at 400000 characters. A workspace outside Git gets no diff and the old instruction to find scope evidence. Both `review` and the pi `reviewer` use coverage entries `{id,status,evidence}`, where status is covered/finding/unreviewed/not-applicable. A task reopened by `invalidate` or `amend` since its last acceptance gains one `reopened:N` obligation per reason; like task criteria, it cannot be not-applicable, and the same reasons appear in the worker's brief under "Why this task was reopened". Missing coverage in legacy receipts is retained as a gap. A finding is blocking only when it is a regression of existing behaviour, a failed task criterion, a false statement in documentation the task changed, or vendor code or setup for a third-party service that the task added with no source in the workspace or the task's references (an embed or tag snippet, a vendor call's argument order, the steps in a vendor console); a preference, style choice or optional improvement is never blocking. The packet lists the task's `references`, or those supplied to `delegate`, `reviewer` or `review-packet` for this chunk, so the reviewer can trace such code to its source. The delegate loop answers a first gap with no blocking finding by obtaining exactly one fresh review from another eligible family — not the author's family and not the family that left the gap — and accepts if that review is complete; a retry that cannot be routed returns `route-pending`, and only a second gap escalates as `review-evidence`, leaving the task in review. `review-evidence-needed` is host work, not a completed review or repair cycle. `review-check` input `{id,check:{id,command,args}}` registers an additional unique task check while review is idle, invalidates the old review, and retains repair counters. Execute it with `check`, then obtain updated independent coverage. See [review method](review.md).

Reviewer context includes only settled decisions explicitly marked `purpose: "requirement"`. Use that purpose for user/product requirement facts, never finding disposition, routing or completion judgments. Unclassified legacy decisions stay durable for the host but are withheld from the fresh reviewer; restate relevant requirements in task criteria/constraints or classify them explicitly. This prevents prior verdicts leaking through otherwise factual-looking answers. Previously accepted/completed historical records are not retroactively re-reviewed; the new gate applies to new acceptance transitions.


### Startup network preflight

`preflight`: `{ "network":"restricted|allowed|unknown", "channel":"actual host execution channel" }`. Returns ready or an actionable failure, elapsed time and an artifact reference. Known restricted networking performs zero requests. Otherwise it validates credentials and a fixed synthetic Jev choice with one request attempt and a ten-second timeout. Run before the first network operation using the same permitted execution boundary as later Jev/pi calls. No project content is included, no permission is granted, and no global setting is changed. `doctor` remains a local check; it does not prove network connectivity. An existing run is optional: the supplied run-id provides the diagnostic/artifact location.


### Host actions and diagnostic export

`host-action` records an immutable, local host observation even before run initialization or after an API failure:

```json
{"actionId":"review-attempt-1","sessionId":"host-session-1","kind":"review","phase":"planned","summary":"Request fresh review of the current task","taskId":"layout","next":"Request host network permission"}
```

Kinds: decision, worker, review, edit, check, integration, permission, other. Phases: planned, permission-granted, permission-denied, started, completed, failed, skipped. Use the same action/session identifiers for an attempt's observations, and a fresh actionId for a retry. Summary is required; taskId and next are optional. Summaries should contain concise reasons and local evidence references, never credentials. Logs use existing best-effort secret masking; arbitrary sensitive text is not guaranteed to be detected.

`diagnose` includes this ledger and unreadable-record names alongside runtime diagnostics. These are host attestations, not proof of tool execution or authorization. Missing outcomes need reconciliation; an absent event does not prove the agent skipped a step. Same-timestamp records have no guaranteed causal ordering.

`diagnostic-export` writes a local JSON file under the run's exports directory and returns its path and content. Its structural allowlist excludes free text, prompts, code, original action/session/task IDs, model names, paths, raw tool output and exception messages. It retains pseudonymous action/session relationships, phase/kind, task status counts and runtime outcome/timing/usage summaries. It works without valid run state and reports unreadable record counts. The result still discloses operational metadata; inspect it before explicitly sharing. Nothing is automatically uploaded. Full explanations remain available locally through `diagnose`.

For legacy running claims only, `reconcile-execution` accepts `{id, operation, confirmedStopped:true, evidence}`. Copy the current owner operation exactly (omit when no owner exists). First verify that task execution has stopped, even if its coordinator process remains alive. This trusted host attestation archives the prior task and releases ownership into blocked state; it does not kill any process or remove files. Inspect preserved artifacts, then use `requeue` and route again. Never assert stopped while work is still executing.
