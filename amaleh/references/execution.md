# Route and execute

Inspect `next`, then hand every ready chunk to one `delegate-batch` and follow it with `wait`. The runtime drives the chunk to acceptance autonomously; you handle only escalations, integration and feature-level verification. Chunk-level semantic choices are made by workers through their Jev helper; reserve your own `decide-batch` calls for run-level questions. Independent research targets can be separate tasks; research-only or plan-only requests end with evidence, not compulsory code.

Use `catalog` to obtain current model cards. Worker and reviewer candidates are the `flash` models listed in `amaleh/models.json`; `deep` lists the deeper repair model. A purpose combines model, actual available tools, focused brief and appropriate checks. Filter for image input, tool support, context and access before asking Jev. Current price/capability is a sourced fact; quality and latency are uncertain until observed. Kimi K3 is for supported deeper needs, not all frontend/research. Do not force a cheap failure for a known hard task. Keep the invoking host as coordinator. Task size does not authorize direct implementation.

Prepare isolated task workspaces using the host's supported worktree mechanism or Git worktrees. Preserve relevant uncommitted input explicitly; ordinary worktrees do not copy it. The runtime accepts the prepared absolute workspace; it does not guess a base branch, and it merges nothing automatically. Before `start`, fetch the project's remote and create the run branch from its remote default branch unless the user named another base: `start` fetches that remote, resolves its default branch from the remote HEAD, and refuses a Git checkout whose HEAD does not contain the fetched tip, naming the remote branch and the Git commands that fix it. Input `base.userInstruction`, quoting the user, is the only override; a workspace outside Git or with no remote records `base-unverified` and proceeds. Before `finish`, the runtime fetches the same branch again and refuses while merging it into HEAD would conflict, naming the conflicting files. Prepare each task's isolated checkout from that base, and merge accepted chunks in the run's integration worktree, never in the checkout the skill itself runs from. On non-Git projects, use host-controlled isolation/copy and explicit integration or serialize work. Never give independent workers the main writable checkout concurrently. Each task's `resources` are path globs relative to its workspace (for example `"amaleh/scripts/adapters.ts"`, `"website/src/**"`, `"*"` for the whole workspace); the `delegate` loop holds every worker change to them. After each worker run, and again after every repair, a built-in `scope` check diffs the task workspace against the run's main checkout and fails the chunk when a changed or untracked path matches no resource glob, naming every out-of-scope path so the repair loop can revert or redo it. `scope` is reserved for this built-in check, so no task check may register it. A workspace outside Git has no diff; the check then records that it could not run instead of passing silently, so keep such work honest through the isolation and integration review above. Workers are confined to their task workspace: the worker prompt names the absolute workspace, states that every edit and write must stay under it, and marks the brief, artifacts, Jev helper, contract question helper and run's main checkout read-only. The runtime parses pi's edit and write tool calls against that workspace. When a worker's edit or write targets a path outside the task workspace, the runtime kills the worker's process tree immediately and `delegate` returns `escalated` with stage `workspace-escape` naming every escaped path, without spending a repair cycle or provider failover. The task is left blocked with the escaped paths in its reason; the host is the only one allowed to restore files outside the task workspace, and requeues the task once they are restored. The guard sees only edit and write tool calls; bash and powershell side effects cannot be inspected this way — state the confinement in the brief when a task must run shell commands that write.

Use `delegate` for routed, tracked, autonomous chunk execution: one call runs worker → checks → review → repair until acceptance or escalation. A worker that finishes its run without a final message is not discarded: an empty-summary result, or a reply cut off twice by the model's output limit (the first cut-off is continued once in the same pi session), still goes to checks and review, which judge the actual changes. A reviewer is never continued for length: its JSON report is the whole reply, so a reviewer with no final text fails, and a report cut off by the length limit goes through the reviewer's own format-retry loop, which asks once more in the reviewer's own session so its inspection is kept. A reviewer call that fails for any reason other than a workspace escape or a settled funding or authorization failure is not a lost chunk: the loop replaces it with a fresh review on another eligible family whose call did not fail, bounded by `providerFailovers`, and records a `provider-failover` event with stage `reviewer`. When the budget runs out, `delegate` returns `failed` and the task stays in review with its worker output, ready to delegate again; worker-stage failover still replaces only transient provider failures. The runtime assembles the brief from the task contract; add `brief` only for genuine extra context such as applicable repository instructions, allowed scope nuances, references and real tools. Workers consult Jev themselves through the bundled helper (`scripts/jev.ts`) for uncertain in-task choices — do not relay those decisions through the coordinator. A worker that finds the contract itself wrong raises a contract question through `scripts/question.ts` instead of bending the work to fit it, and `delegate` stops with `contract-question`; see [the command contract](runtime.md). Workers never write vendor code or setup for a third-party service from memory: put the vendor's documentation among the task's `references`, or expect a contract question asking for it. Every worker command must end on its own; one that starts a JavaScript runtime waiting for a debugger (`--inspect-brk`, `--inspect-wait`) is stopped at once. Built-in pi tools do not include a general web-search connector: for web research, supply retrieved source artifacts or have the host use its retrieval tools and record results. For vision provide actual accessible image files and a verified image-capable model; do not infer appearance from source alone. Flash workers may use read on images when supported by pi. Direct `worker` calls remain for the granular legacy flow, not for ordinary chunks.

Native subagents may be used only when they can actually execute the exact model selected by `route` in a clean context. Pass its `decisionId` as `routeDecisionId` to `claim` before launch, then record actual launch identity and `result`. Do not relabel an Astra subagent as a Flash worker or use its convenience as a routing exception. Respect capacity and resource locks. No nested delegation by default. Carry forward protocol metadata in pi sessions rather than rewriting message histories.

Run registered task checks. Review a coherent task, accept when current checks and review pass, then integrate actual changes through host tools. Inspect merge conflicts and cross-task interactions, record integration evidence, and run full relevant integration checks against the final result. Commit/PR/publication follow existing user authorization; Amaleh does not add authorization.

Do not stop at `next: review`, `repair`, `integrate`, or `verify-feature`: these are your next actions. Continue until `done` or an actual external blocker. While a batch runs, stay in the `wait` loop and handle each finished chunk as it arrives; never end the turn on "launched, waiting". Reconcile live ownership before restarting anything: `next` returns `resume` when a recorded owner is gone.

## Automatic model routing

`worker` and `reviewer` automatically load current OpenRouter cards, filter eligible candidates, and select deterministically by round-robin seeded by the run's session hash: each routing decision in the run advances the rotation, so eligible families alternate instead of fixating on one vendor. No Jev call is spent on mechanical model selection. Omit `model` to use this route; an explicit model is only an assertion and must match the recorded selection. Worker candidates are the `flash` models listed in `amaleh/models.json` that the live catalog shows with tool support; asynchronous `:batch` endpoints are excluded because they are not interactive. Review candidates exclude the author's family, so the pool needs more than two families: with only two, one vendor outage leaves every task built by the healthy family with no eligible reviewer. The rotation counter is read inside the transaction that records the decision, so concurrently dispatched chunks receive different models rather than all reading the same count. A model whose launch exhausts its retry budget on a transient provider failure is recorded as unavailable and skipped for five minutes; when every eligible model is cooling down the rotation proceeds anyway rather than blocking the run. 'Provider returned an empty response', 'Stream ended without finish_reason' and 'The model stopped before completing the response' are among those transient failures: the launch retries them, and an exhausted budget re-routes the chunk to another family instead of failing the task. A model measured at least twice as slow as the median for the same role (worker or reviewer) over `slowModelWindowMs` is skipped for that role only, and returns once those slow calls age out. Failed and timed-out calls are recorded as speed samples with their elapsed time and a `failed` marker, so they count toward that measurement too. Every worker and reviewer call stops at its configured wall-clock limit (`workerTimeoutMs`, default 5400000 ms, and `reviewerTimeoutMs`, default 2400000 ms; `0` disables the limit), and a call stopped by it is failed rather than retried as transient. A model slow at reviewing still writes code. See [the command contract](runtime.md#diagnostic-traces). The runtime records eligible cards, price/capability data, decision and actual model in diagnostic/state evidence. It does not claim vendor descriptions prove quality or speed.

Pass `routing: {role, requiredInputs, contextTokens, evidence}` to select a configured purpose pool or impose additional requirements. A named role must exist in `pools`. Supply observed strengths, measured latency or other grounded suitability evidence in pool notes and routing evidence. A specialist pool may contain models outside the default families; the full live catalog is available. Deep repair enforces Kimi, and host-depth work returns native host takeover rather than launching another Flash worker.

Routing never pends on Jev: eligible rotation always resolves. Legacy pending routes still return `host-decision`; record the resolution, then retry the original operation. `route` can preview and checkpoint selection before dispatch. Selecting `reassess` or finding no eligible candidates returns `route-blocked`; revise the task/pool/evidence, then route again. Service errors remain errors, not permission to bypass routing.

Routing receipts bind task contract, repair cycle, dependencies, pool, requirements and (for review) the current content fingerprint. They are consumed once. Unrelated task checkpoints do not invalidate them. Changed inputs require a new route and supersede stale pending routing questions. All worker claims, including native execution, consume a matching worker route. Plain claims are rejected. Direct host implementation needs a `host-exception` authorization instead; never consume a worker receipt and then do its implementation in the coordinator.

Worker context is task-specific: it retains run intent/constraints, all unscoped settled decisions, the task's and dependency tasks' routing decisions, and dependency artifact references. It excludes unrelated task routing and the coordinator's global next-action instructions. Originals remain in the durable revision named by the packet. This does not truncate arbitrary decisions by age or replace pi's original session metadata.

Before loading catalog cards or asking Jev, worker routing checks dependency integration, worker capacity and live resource/workspace conflicts. `dispatch-blocked` names the prerequisite or owner to reconcile; it is not a model-suitability judgment. Resource conflicts understand globs: two resources conflict when the directory one of them matches under contains the other's. Retry after that condition clears. Claim still rechecks the same constraints transactionally because another task may start while routing is in progress.


## Network launch boundary

Before Jev, catalog, worker or reviewer calls, inspect the host's effective network permissions. On Codex, when networking is explicitly restricted, launch the required network operation using the host shell tool's supported `sandbox_permissions: "require_escalated"` request with a precise destination/payload justification. Do this before attempts in the blocked sandbox. Approval remains controlled by the host. On Claude or another host use its supported network-permission mechanism; never assume Codex flags exist there. No global config edits, permission bypass, proxy workaround or unsandboxed background helper.

Run `preflight workspace run-id input.json` once per current execution boundary. Input is `{network:"allowed",channel:"Codex approved shell invocation"}` only when that describes the actual launch. Use unknown when permission is uncertain. Restricted returns network-permission-needed without reading credentials or making requests. The actual probe sends only a fixed synthetic 1-versus-9 decision via the same adapter and pi credential source as ordinary Jev requests. It makes one attempt, bounded to ten seconds, and archives a credential-free result plus diagnostics. Ready means this probe succeeded; it neither grants persistent permissions nor proves pi worker availability. Keep subsequent network launches in the same approved boundary; ordinary commands do not inherit an earlier elevated call's permission. Subagents need the same instruction and must not silently revert to restricted launches.

If a permission request is denied, retain the blocker and explain the denial; do not relabel it as Jev uncertainty or try an indirect route. Separate network-unreachable (cause not proven), credentials-needed, credits-needed, provider-access-denied, provider-unavailable, jev-protocol-error and jev-verification-needed. Do not repeat a known permission denial as transient network retries. Existing normal request retries remain for actual transient failures.

Permission to run a synthetic probe is not permission to export repository content. Use the user's existing authorized scope for necessary task briefs/code/evidence and state it accurately in approval requests. An explicit export rejection must be resolved before sending that payload. Preflight is a host startup procedure; the runtime does not inspect or modify host permission policy and does not claim to enforce session identity.

## Direct host exceptions

`host-exception` accepts only `user-request` (cite the explicit instruction for this task) or `repair-escalation` (persistent Flash and deeper repair allowance exhausted, task at host depth). Use its returned authorization as `hostAuthorization` in `claim`, with the actual host model. The grant is single-use and expires when the bound task contract, host, repair policy or repair state changes. All dependency, capacity and conflict gates still apply. Host work is final: no model reviews it. Before `result`, re-read your own diff against the task criteria and every reopen reason. Then `delegate` the task: it runs the registered checks and `scope` and accepts when they pass, or returns `host-checks-failed` without spending a repair cycle. See [host work is final](review.md#host-work-is-final).

`delegate` returns `escalated` with stage `host-takeover` for a task at host depth. It is a signal to record the repair exception, not permission to skip claiming. A `host-decision` resolving Jev uncertainty only selects an eligible option. A blocked network/API does not permit silent host implementation. Preserve the blocker or use a genuinely authorized supported execution channel. User-request evidence is a trusted host attestation; the runtime cannot independently verify conversation consent.

For `reconcile-execution`, inspect live ownership and preserve existing artifacts. Do not continue an old running claim without authorization or fabricate a historical route. Reconcile stopped ownership through recovery, then route the requeued task. Work already returned for review is not retroactively discarded.

For legacy running claims only, `reconcile-execution` accepts `{id, operation, confirmedStopped:true, evidence}`. Copy the current owner operation exactly (omit when no owner exists). First verify that task execution has stopped, even if its coordinator process remains alive. This trusted host attestation archives the prior task and releases ownership into blocked state; it does not kill any process or remove files. Inspect preserved artifacts, then use `requeue` and route again. Never assert stopped while work is still executing.
